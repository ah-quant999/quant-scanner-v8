```
! [rejected]  HEAD -> main (fetch first)
hint: Updates were rejected because the remote contains work that you do not have
⚠️ push 被拒（远端已前进），同步远端并按最新 raw_data 全量重建后重试 (1/3)
```

**同刻还有交叉证据**：`v8_risk_gauge` 09-15 00:42 的 failure step 恰好是「📤 推送 raw_data/risk_gauge.json」。
⇒ 00:4x CST **多个 workflow 同刻抢 main**，现有退避（3 次、且每次要「全量重建 data/*.js」，单轮 2~4 分钟）**不足以免开竞争**。
**修法（一劳永逸，别靠重跑）**：
① 部署步的重试改**指数退避 + jitter**（如 5s/20s/60s/180s，各带 0~30% 随机抖动），缩短单次重建耗时或把「重建」与「push」解耦（重建一次、push 多次重试）；
② 整点/半点**错峰**：把 `risk_gauge`、`backup`、`build_deploy` 的 cron 从同一分钟拆开；
③ 更彻底：所有「推 main」的动作走**同一个串行队列**（独立 concurrency group + 队列文件），杜绝跨 workflow 抢推。

⇒ 这是**机级/runner 级故障**，不是代码 bug：job 在 runner 上从未真正开始，**不可能靠重跑解决根因**。
**修法方向（一劳永逸）**：

   自动**重排一次**（一次性、带去抖，避免变成高频重试风暴）并打 annotation，而不是靠人巡检发现；
② runner 侧加心跳/磁盘/内存预检（`lemoncat-cn` 同刻是否在跑别的 job 导致资源不足，需要 runner 侧日志才能定论——我这边 API 拉不到）。
