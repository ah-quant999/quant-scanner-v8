全站「更新时间 vs 数据」一致性审计报告

审计日期：2026-08-09（周日，A股休市；上一交易日 2026-08-07）· 范围：stock-scanner 全站 data/*.js + index.html 时间展示层 · 铁律：不弄虚作假、旧数据不蒙混、没有就标注原因

一、审计结论（先说结果）

✅ 展示层总体诚实：所有时间展示都基于真实数据时间戳，没有谎称「今日」、没有用批量重打包戳蒙混。

但发现 1 处「旧信号被更新戳混淆」已修复，另有 2 处需后续根治（见第三节）。

二、逐项核查（展示层 vs 真实数据）

通过无硬编码假「今日」

index.html 中全部「今日已计算 / 今日已跑完 / 今日已入仓」字样均出现在 _runBadgeInfo 等动态函数内，由真实数据日期与当前北京时间比对得出。今天周日，RPS 屏正确显示 08-08 已计算、三重共识显示 08-08 已跑 / 已入仓 0，无一处谎称「今日」。

通过展示读取真实戳，未用重打包戳

所有胶囊/徽章读取 update_time / data_time / calc_date（8/7–8/8 真实值）。批量重打包时在 56 个文件写入的 build_time:"2026-08-09 11:15:54" 字段（原报告误写为 time，已纠正），经全局 grep 在 index.html 中零引用，未被任何展示路径使用。

通过新鲜度判定未被重打包戳误导

guard_v8_freshness.py 提取各文件 update_time 比对「最近交易日收盘」；freshness_status.json 的 core_stale:0 基于此真实戳。判定口径未被 8/9 重打包戳污染。

通过缓存 ?v= 戳准确

各数据脚本 ?v= 等于该文件真实数据日期（CANDIDATE/LHB_DATA 数据确为 8/7 → ?v=20260807；RPS 为 8/8 → ?v=20260808）。缓存失效逻辑正确，不会出现「内容更新但戳不变导致旧缓存常驻」。

通过引用文件全部存在 · 缺失即标注

index.html 引用的数据文件全部存在于 data/，无悬空引用。三重共识 count:0 如实显示「已入仓 0」，未编造入选股。

三、发现的问题与整改

已修复问题1：驾驶舱建议信号陈旧被「更新于」戳混淆

现象：COCKPIT_ADVICE.js 共 11 条信号，signal_date 全部为 2026-07-07 ~ 07-09（一个月前），卡头却显示「更新于 08-08」。虽每只已标「07-09入」，仍容易被视为新建议。

整改：commit 03f5022a。在「回测驱动关注」卡顶部新增警示横幅——当最新信号日期早于最近交易日时，明确标注：⚠️ 信号数据较旧（最新信号 07-09）· 早于最近交易日 08-07，非当日新信号，仅供参考，请勿据此新建仓位。

已修复问题2：批量重打包戳 build_time → republish_time

纠正：原报告误把字段写成 time，实际字段是 build_time，写入 56 个 data/*.js（由 update_v8.py 统一注入）。

整改：修改 update_v8.py，将 build_time 重命名为 republish_time，并加注释明确「仅用于排障与缓存戳，前端不得当作数据时间展示」。全量重建 56 个 data/*.js 与 index.html cache-busting。

已修复问题3：健康检查增加 signal_date / enter_date 偏差检测

整改：在 v8_health_check.py 新增 check_signal_date_freshness()：读取 COCKPIT_ADVICE.js 的 watch[].signal_date 与 FINAL_RECOMMEND_DATA.js 的 stocks[].enter_date，取最大值与「最近交易日」比对；若信号日期早于最近交易日，则 page="内容审计" warn 告警，并绕过 self_heal 自动派发（内容级陈旧需算法/数据根治，不能简单刷新）。

实测：2026-08-09 15:52 运行即检出「驾驶舱建议最新 signal_date 2026-07-09 早于最近交易日 2026-08-07」。
