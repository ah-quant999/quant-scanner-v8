### 根因 2｜显式 stage 陷阱（设计缺陷，最危险）

云端唯一决策点 `.github/scripts/v8_stage_gate.py`：

```python
PREREQ = {"A": None, "B": "A", "D": "B", "E": "D"}     # 严格串联

if explicit in ("A", "B", "D", "E"):                    # 人工/自动指定的批次
    pre = PREREQ[explicit]
    if pre is None:            return (explicit, True,  "显式 X（最上游，无前置）", ...)
    if ready[pre][0]:          return (explicit, True,  f"显式 X，前置 {pre} 已就绪", ...)
    return (explicit, False, f"⛔ 显式 {explicit} 但前置 {pre} 未就绪 —— 拒绝执行，否则会用陈旧数据算出假新鲜产物", ...)
```

且闸门 docstring 明写：「上游未就绪 → stage_ok=false → 调用方**必须红灯 + 拒绝执行 + 紧急报告**」。

**两个恶果**：

1. **假失败**：E 档 21:05 唤醒时若 D 批未跑完 → `stage_ok=false` → 整轮变红 → 触发告警邮件，而这一秒活都没干。
2. **本该发生的接力不会发生**：即使 D 缺、指定 E 也只会红/空转，**永远不会去跑 D** —— 最终推荐断档。

（本机 `v8_night_postclose_watch.py` v1 的第 284 行同样是 `client_payload: {"stage": stage}`，同型缺陷。）

### 根因 3｜yml 承诺的「调度主力」从未存在

`v8_algo_cloud.yml` 第 42–43 行、第 66 行两处注释都写着：

> 「真正的调度主力 = 本机『盘后算法链接力推进器』自动化（每小时 :10，**16:00-08:59**），以下 cron 仅作备份。」

⇒ **系统的设计文档假定了一个不存在的组件**，所有冗余兜底（D/E 派发器）一 PAUSED，就彻底裸奔。

## 四、防踩踏 / 防风暴 —— 四道串联闸门

| 闸 | 机制 | 位置 |
|---|---|---|
| ① **幂等** | 闸门按**内容级**「缺什么跑什么」；产物全就绪 → `target=NONE` 空转（合规真成功，不是假成功）⇒ 重复唤醒绝不抢跑 | 云端 `v8_stage_gate.py` |
| ② **不打扰在跑的** | 任一 run 处于 `in_progress / queued / pending / requested / waiting` → 本班直接退出、不派发 ⇒ 并发组「**1 跑 + 1 排队**」的上限永不被突破 | 各派发器 + 推进器脚本 |
| ③ **冷却期** | 距上次派发 < 20–25 分钟不派；单轮最多派 1 次；**严禁循环重试** | 各派发器 + 推进器脚本 |
| ④ **零成本空转** | 推进器**先本地读产物判新鲜度**，三批全新鲜 → 记 DONE 直接退出，**不产生任何 GitHub run** ⇒ 每天 34 个班次里绝大多数不动用 runner | 推进器脚本 |

**并发组配置（未改动，本就正确）**：`concurrency: {group: v8-algo-cloud, cancel-in-progress: false}`
—— `false` 是刻意为之：算法链单轮 20–40 分钟，**绝不能被新派发打断**（会丢产物）。

> 结论：唤醒源可以任意多、任意频繁，因为「是否真跑、跑哪批」由幂等闸门裁定；
> 派发端只需守住 ②③ 两条，就不会出现历史上「每 2 分钟一次自激风暴」。
