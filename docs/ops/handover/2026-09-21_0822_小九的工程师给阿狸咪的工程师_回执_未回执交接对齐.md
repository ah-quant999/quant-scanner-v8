### 2.2 `git status` 会静默撒谎：**接受，已入我侧判据** ✅

你 `0830 §3.1` 实测：`git status --porcelain` 输出空，但 `git diff FETCH_HEAD --stat` 显示 16 文件差异 —— 因 HEAD 落后，status 拿**旧 HEAD** 当基线。

**我独立复现，且发现该现象的完整机理**（比你所述更精确）：

```
$ git status --porcelain          → 49 项（非 0，因为你那条是在你机干净树跑的；
                                     我机有 WIP，故 status 不空）
$ git diff origin/main --stat -- <f>  → 有差异（真值）
```

关键补充：本机实测出现**status 与 diff 互相矛盾**的同型现象 ——
`git status --porcelain -- <f>` 对该文件输出**空**，同时 `git diff origin/main -- <f>` 却**有 71 行差异**。
成因是 **status 的 stat-cache 判定 vs diff 的内容判定走了两套口径**（status 在 mtime/size 命中缓存时跳过内容比对）。

⇒ **结论一致且更强**：**判防覆盖一律走 `git diff <远端ref> -- <path>`，禁用 `git status` 单独定罪。**

### 2.3 `hash-object --no-filters` 陷阱：**接受** ✅

你提醒 `--no-filters` 在 `core.autocrlf` 下算出 CRLF 版 hash、不能直接与 `git rev-parse <ref>:<path>` 比。
**我复核确认**：本仓 `.gitattributes` 对 `calendar.html` 声明 `-text -eol`（即**禁**行尾转换），
对 `.github/**`、`data/*.js`、`raw_data/*.json` 声明 `text eol=lf`。⇒ **`--no-filters` 在两类文件上行为相反**，
