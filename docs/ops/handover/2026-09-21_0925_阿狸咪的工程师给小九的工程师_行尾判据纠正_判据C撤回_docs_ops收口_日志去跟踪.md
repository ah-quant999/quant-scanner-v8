## 一、🔴 先纠正我上轮的错误结论（我错了两次，都得记下）

### 1.1 「永久脏 18 个 → 17 个」是**错的**，真值是 **0 个**

我上轮的判据：`git ls-files --eol | awk '$1=="i/crlf" && $2=="w/crlf"'`
**漏了第三个必要条件 `attr 含 eol=lf`。**

「永久脏」的**完整判据是三元组**：

```
i/crlf  ∧  attr 含 eol=lf  ∧  w/crlf
```

含义：**入库 blob 是 CRLF，属性却要求 LF** ⇒ clean filter 输出 LF ≠ 库中 CRLF ⇒ 结构性不等、永不可能收敛。

实测（本轮）：

| 检查 | 结果 |
|---|---|
| `i/crlf` **且** `attr 含 eol=lf` | **0 个** ← 真·永久脏，全仓为零 |
| 那 17 个的 `git status` | **全空（不脏）** |
| 那 17 个的 `git diff HEAD` | **无差异** |

⇒ 它们是「blob=CRLF + 无属性 ⇒ blob 与工作树同为 CRLF ⇒ git 判为一致」的 **无害态**。
**我上轮把「一致态」误报成了「永久脏」，并据此提出「根治 17 个」的假任务。** 抱歉。

### 1.2 「`normalize_eol.py --check` 会误报 30+ 个」——表述也不准确

准确说法见 §三：它报的路径**确实**属性要求 LF，问题不在「报错」，而在**它把两类性质相反的文件混在一起并全部就地写入**。

## 三、`normalize_eol.py`：真伪两分（本轮实打实的修复）

### 3.1 问题的真正形态

它报出的文件里，**藏着性质完全相反的两类**，而旧版把两者**混在一个 `changed` 列表并全部就地写入**：

| 类别 | 判据（**入库 blob 是否含 CR**） | 性质 | 处置 |
|---|---|---|---|
| **real 真问题** | `blob_cr > 0` | blob 本身 CRLF 而属性要 LF ⇒ **结构性不等，必须收口** | **自动写入** |
| **cosmetic 非问题** | `blob_cr == 0` | blob **已是 LF**，仅工作树 CRLF（autocrlf 正常检出态）⇒ clean 后 = LF = blob ⇒ `git status` **为空、git 判为不脏** | **默认跳过**；改它只会让这些文件进下次 commit = **制造假 diff** |

实测本仓：cosmetic 类 **86 个** ⇒ 照旧逻辑跑一次会**无端改动 86 个文件**。

### 3.2 改了什么

- 新增 `_index_blob_cr()`：用 `git ls-files -s` 取索引 blob sha + `git cat-file --batch` 批量读回数 CR（一次进程，不逐文件起）。
- `run()` 按判据分 `real` / `cosmetic`，**写入只对 real**。
- 新增 `--include-cosmetic` 开关（确要一并改才生效）。
- `--check` 输出改为**分类报告 + 明确告警**，并说明「已跳过不写」。
- docstring 新增「真伪两分」章节 + 撤销命令说明。

**实测**：真问题 0 个、非问题 86 个（已自动跳过）✓

### 3.3 🔴 一条独立判据：补规则**不会**自动改 blob

**普通 `git add` 对 stat 未变的文件会跳过 clean filter** ⇒ 加完 `.gitattributes` 后跑 `git add`，**blob 一动不动、静默无效**（我本轮踩过：跑完 add 发现 4 个文件都没进暂存区）。
**正确命令：`git add --renormalize <显式路径>`。**

## 五、裁定：`STOCK_QUOTE.js` / `STOCK_LIST.js` **不移出 git**

实测依据：

| 项 | 事实 |
|---|---|
| 体积 | `STOCK_QUOTE.js` **3.87 MB**（9988 只：A股 5564 + 港股 2803 + ETF 1621）；`STOCK_LIST.js` **1.99 MB** |
| 前端加载 | `index.html:622-624` 明写「**A2 懒加载**：STOCK_LIST / STOCK_QUOTE 移至文末 loader **按需注入**」⇒ **不阻塞首屏** |
| 部署链依赖 | **4 个 workflow**（`v8_stock_quote_refresh.yml`、`..._cloud.yml`、`cloud_weekly_cleanup.yml`、`v8_algo_run.yml`）在读/写这两个文件 |
| 传输成本 | 已在 2026-09-21 凌晨优化：CDN `Range` 分块续传 + gzip + keep-alive，`v8_algo_run.yml` 实测 **2.75× 加速**、4 个大文件 **16/16 sha1 全等** |

**裁定：不移出。** 理由：
1. 已是懒加载 ⇒ 移出的**收益（首屏）本就已被拿到**
2. 移出需**新建下发通道**，而前端铁律是「数据必须读 `window.X` 注入，禁止 `fetch('../data/...')`」⇒ **违反铁律 + 风险大**
3. 4 个 workflow 依赖 ⇒ 改动面大
4. 盘中高频刷新是为「数据新鲜」（宗旨①），**降频会伤新鲜度** ⇒ 与宗旨冲突
5. 真实成本（回退同步下载）**已在上一批用分块+gzip 解决**

> 若将来确要瘦身，**正解是「字段精简」而非「移出 git」**：`concepts`/`industry` 为静态元数据、
> 却在每只股票上重复存字符串。改为「概念 ID + 字典」可显著降体积，且**不违反铁律、不降新鲜度**。
> 但它改变**数据契约**（前端 + 生成器双改），需门禁 + 回测验证 ⇒ **须单独开批次，不在本轮做**。
