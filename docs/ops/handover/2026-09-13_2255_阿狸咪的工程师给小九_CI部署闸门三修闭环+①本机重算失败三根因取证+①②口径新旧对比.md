## 二、独立问题：`?v` 提交前核验是「假 failure」（`064b71fbf`）

### 2.1 事实

| 环节 | 实测 |
|---|---|
| 核验判据（workflow L307） | `sha1(去 republish_time 后的内容)[:10] == index.html 里的 ?v` |
| 实际写入者 `update_v8.py::_data_file_update_time()` | 自 **2026-09-10** 起写的是**单调 unix 秒令牌**（L738-747 注释自陈原因：原内容哈希在「数据被回滚到旧内容」时哈希**不变** ⇒ 浏览器永久吐旧副本） |
| 判据 vs 写入 | **不同源** ⇒ **恒报失配** |
| 实证 | run `34763191682`（**success**）日志仍打印 `❌ ?v 仍失配 …` **97 项、全部同一戳** —— 而「全部同一戳」正是「单次构建统一令牌」的**正确表现** |

### 2.2 为什么必须修

这是**假 failure**：不阻断部署（末尾 lambda 会白跑一次 `update_v8.py --only-cache-busters` 兜底），但
- 让审计者/后续会话误判为真故障（「97 项失配」看起来极像严重污染）；
- 每轮构建白跑一次全量 `?v` 重写。

> 🔴 与「禁假 success」是**同源的镜像问题**：假 success 掩盖真问题，假 failure 制造不存在的问题 —— 两者都让人**无法信任 run 的结论**。

### 2.3 修法（判据与写入口径对齐）

改为核验**令牌形态**：全部 `?v` 为纯数字（unix 秒）⇒ 通过；出现 16 进制 sha1 形态 = 旧口径写入者回潮 ⇒ `::warning::` + 重写一次兜底。
用 `::warning::` 而非 `::error::`：形态异常属「需人工确认」，不在判据刚被修正的当口贸然阻断部署（防「用新判据造成新假 failure」）。

**未动**：L306 `update_v8.py --only-cache-busters` 保留（构建戳注入後仍需重写）；不改任何 `data/*.js` 与 `index.html` 令牌值；不引入新依赖。
