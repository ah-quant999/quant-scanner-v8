## 三、根因链（四步，可复现）

```
① checkout@v4 后工作树因 raw_data/*.json 的 CRLF 归一化显示为「未提交差异」（脏树）
② push 被拒（远端已被其它高频 CI 推进）⇒ 进入重试分支
③ rebase.autoStash 生效 → 但 pop 冲突 → 无 rebase 可继续 → fatal: no rebase in progress
④ `git rebase --abort` 自身非 0（无 rebase in progress）⇒ `exit 1` 早退 ⇒ 3 次重试失效
```

**触发条件** = 「脏树存在」∧「推送时远端已前进」—— 后者在 v8 的推送密度下**几乎是常态**。
⇒ 这解释了一个现象：`v8_risk_gauge` 今天 **4 次 success（08:27 / 10:17 / 12:06 / 13:42）+ 1 次 failure（15:43）**
—— **不是偶发抖动，是「恰好撞上远端前进」才炸**，属于**低频但结构性**的缺馅。

照抄 `v8_cn_fetch_experiments.yml` L110–117 的既有范式：

```yaml

#   现改用 api_push_raw.py（GitHub Contents API，零 git fetch，免疫 cn git 墙）

```

⇒ **零 git 交互 ⇒ 脏树/并发/rebase 三个问题一次性消失**。改动最小、风险最低、与已治本的两支同构。

### 方案 B（最小兜底 · 保留 git 路径）

在推送步**开头**显式关掉行尾归一化，并在 rebase 前丢弃「虚拟脏」：

```bash
git config --global core.autocrlf false
# 已 commit 过需要保留的文件；此处脏项仅为 CRLF 虚拟差异，可安全丢弃
git checkout -- .
```

并把 L59 的 `{ git rebase --abort; exit 1; }` 改成
`{ git rebase --abort >/dev/null 2>&1 || true; continue; }`（**保住 3 次重试的语义**）。

> ⚠️ 方案 B 只治「CRLF 虚拟脏」这一种脏源；若将来有真实未提交改动仍会复发。**故推荐 A。**
