## 四、一劳永逸根因修复（**不要重跑**）

### 方案甲（推荐·最小改动·语义正确）

**盘中闸门必须区分 `kind`：`t1` 放行，`trading` 拦截。**

盘中拒绝长任务的**原始动机**是「交易日的 A 批采集正在跑，别抢 runner」。
但 `kind=t1`（周六/假期首日）**当天不开市**，不存在采集竞争 —— 拦截它纯属误伤。

在 `v8_algo_cloud.yml` 盘中闸门段，条件是 `TGT != NONE`：

```
# 改前（无条件拦截）
if [ "${HHMM}" -ge 930 ] && [ "${HHMM}" -le 1500 ]; then
    echo "target_stage=MARKET_HOURS_BLOCKED" >> "$GITHUB_OUTPUT"

# 改后（T+1 / 周末批放行）
if [ "${HHMM}" -ge 930 ] && [ "${HHMM}" -le 1500 ] && [ "${KIND}" != "t1" ]; then
    echo "target_stage=MARKET_HOURS_BLOCKED" >> "$GITHUB_OUTPUT"
```

`KIND` 由闸门输出 `chain_kind` 提供（`trading` / `t1`），闸门步已能取到，无需新增依赖。

**⚠️ 配套（不改就漏）**：盘中放行长任务会占用自托管 runner。建议同时给该 job 加
`timeout-minutes: 90`（防 09-11 那种 in_progress 挂 1.7h 占槽）。

### 方案乙（备选·更保守）

保留盘中全拦，但把 **T+1 批的合法时窗从盘中迁到盘后**：
- 在 `check_ready(kind='t1')` 的 `floor` 里，把 T+1 批起点设为 `18:00` 之后；
- 同时把周六/周日 16:40+ 的 cron 唤醒点保留。

代价：**周六当天白天拿不到更新**，要等晚上 —— 但至少不死锁。
**若主人希望周末白天能看数据，就选甲；若宁可稳也不占 runner，就选乙。**
