## 二、改了什么（逐条，可核）

### 1. `algorithms/gen_algo_track.py` —— 分档渐进跟踪（主人令②）

**原缺陷（远端实测）**：`_advance_tracking` 唯一出场条件是 `days_in >= WINDOW_DAYS(90)` 的
`timeout`；而 stats **只从已出场 history 结算** ⇒ 线上 `raw_data/algo_track.json` 实测
`tracking=108 / history_samples=0`，且

```python
wr = round(win / total_decided, 4) if total_decided else 0   # ← 无样本写 0
avg_r = round(sum(eps) / len(eps), 2) if eps else 0          # ← 同
```

⇒ 前端把「**还没样本**」画成「**0% 胜率**」= 视觉假数据。

**修法**：
- 新增 `HORIZONS = [5,10,20,30,45,60,75,90]`，逐标的取「入场日→今日」真实收盘序列
  （`raw_data/kline_cache/<code>.json`，tracked 产物）→ 入场满 5 个交易日即出 T+5，
  之后逐档长出，**不必等 90 天期满**。
- 🔴 **口径诚实铁律**：序列**只取缓存日线**，绝不把「缓存末日 → 今日实时价」当成一个
  交易日接在尾部 —— 缓存落后 N 天时会把 N 天算成 1 天 → 档位索引错位 = 假前向收益。
  实时价只用于 `unrealized`（当日浮动）。
- 无样本档位 `samples=0` 且 `win_rate/avg_return = null`；新增 `coverage`
  （有序列数 / `bar_asof` 数据截至日 / T+5 就绪数）把「累积进度」暴露出来。
- `win_rate` / `avg_return` 无历史样本时由 `0` 改 **`null`**。

**实测**（远端内容副本 + 真实 kline_cache）：
```

T+10  34 样本  胜率 20.6%  均收益 -6.21%   best +22.11%  worst -23.70%
T+20 及以上：samples=0（样本未成熟，前端显示「累积中」，不是 0%）
```

### ⚠️ 发现项 D1（**已实证 · 建议尽快修 · 非本轮引入**）

`v8_build_deploy.yml` **L307 的「提交前 ?v 核验」判据已失效，每次 build 固定误报**：

```python
# 现行（失效）判据：把 ?v 当 sha1 内容哈希比对
... hashlib.sha1(re.sub(r'"republish_time"...',...).encode()).hexdigest()[:10] != v ...
```

而 2026-09-10 主人令已把 `?v` 改为 **unix 秒单调部署令牌**：

```python
# update_v8._data_file_update_time() 现行实现
if _UPDATE_TOKEN is None: _UPDATE_TOKEN = str(int(time.time()))
return _UPDATE_TOKEN          # ← 10 位纯数字，不是 sha1
```

**实证**（远端 `97144729a` 内容）：`data/DO_NOT_DELETE.js` 内容 sha1[:10] = `252f0fe179`，
而 index.html 里它的 `?v=1789140305` ⇒ `sha != v` **恒为真** ⇒ `bad` 永非空 ⇒
**每次 build 都打印 `❌ ?v 仍失配` 并无条件再跑一次 `update_v8.py --only-cache-busters`**。

- 危害：① 日志常驻假警报，**真正失配会被这个噪声淹没**；② 每次 build 冗余重跑一次；
  ③ 该步 `check=True`，第二次调用若失败会直接把 job 打红。
- 不改的原因（诚实说明）：① 非本轮引入、不产生数据错误；② 修法需动 CI 关键步骤，
  而我在阿狸咪机上**无法端到端验证一次真实 build**，不敢未验证就改 CI。
- 建议修法：把判据从「sha1 比对」换成**一致性核验** ——
  `update_v8 --only-cache-busters` 同一进程内所有 `?v` 必为同一令牌，
  故核验「index.html 中存在对应 `data/<F>.js` 的引用，其 `?v` 去重后只应有 1 个值且为 10-12 位数字」，
  不一致才重跑。这样既保留守卫意义、又不误报。

## 四、本轮踩到 3 个坑（已固化防御，勿重犯）

1. **guard 子串必须「新文本独有」**：patch21 用 `"已扣双边交易成本"` / `"cost_bps_per_side"` 当
   「是否已应用」的守卫，而这两串在 `strategy_four_volume.py` **别处本来就存在**
   （L489/L447）⇒ 被误判为已应用而**静默跳过**，漏改 2 处（已用 `1362308e2` 补推）。教训：
   guard 取新插入文本独有的整行片段。
2. **`git archive` 会按 `.gitattributes` 做 eol 转换**：它把纯 LF 的 `index.html` 输出成 CRLF
   ⇒ 拿 archive 出的副本量行尾会得出**错误结论**（实测仓库 blob `index.html` 是 CR=0/LF=14792）。
   校验副本一律用 `git show <sha>:<file>` 的真字节；测行尾必须**二进制读**
   （`grep -c $'\r'` 在 Git Bash 会把纯 LF 报成满是 CR）。
3. 附带：脚本注入 `index.html` 的锚点**不能写死 `?v=` 数字**（CI 每次 build 都用内容 sha 重写
   缓存戳，字面锚点下一次构建后必然失配 → 命中 0 → 静默不注入）。已改用正则锚点。

   附带②：`logic.html` 是 **CRLF**（实测 CR=8651/LF=8651）、`index.html` 是 **LF**（CR=0/LF=14792）
   —— 补丁脚本必须**按原文件形态守恒**（LF 比对 + 按原形复原），否则会整文件重写。
