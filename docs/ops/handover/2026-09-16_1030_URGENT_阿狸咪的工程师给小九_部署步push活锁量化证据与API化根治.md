## 2. 一劳永逸修法（三选一，甲最佳；均**不要重跑**）

### 甲（推荐·最彻底·符合本仓既定范式）：部署步弃用 `git push`，改走 Contents API / Git Data API

- 依据：本仓**已有定论**——`v8_cn_fetch_experiments.yml L109-113`、`v8_health_patrol.yml L260-265` **已改用 `api_push_raw.py`（Contents API）**，`v8_build_deploy.yml L186` 自家注释也写着「⚠️ 不要改回 `git rebase`」。
- 原理：`git push` 有 **fast-forward 前提**（本地 HEAD 必须是远端 tip 的后代），所以「构建 105s ⇒ 必然落后」；而 **Contents API 是「对远端当前 tip 的按文件合并」，没有这个前提**，天然免疫抢推。
- 落地：
  1. 构建段（`update_v8.py` 全量）**原样不动**；
  2. `git diff --cached --name-only`（或 `git status --porcelain`）产出变更清单 → 交给 `api_push_raw.py` **逐文件 PUT**；
  3. `index.html` 是本仓唯一有「人工改动 + 构建产物」双重身份的文件，对它加 **`expected sha` 校验**：sha 不匹配 ⇒ 重取 tip → **只重放 ?v 戳 + guard 对齐（秒级）** → 重 PUT。**不要重跑全量构建。**
- 残余风险：仅「同秒两写者改同一文件」。`data/*.js` 由本 build 单一生产 ⇒ 风险≈0；`index.html` 有守卫，可控。

### 乙（次选·改动最小·非 100%）：把「重建」从 push 前关键路径摘掉

- 重试路径加一步**判据门**：`git fetch` 前后若 `git diff --stat <old_tip> FETCH_HEAD -- raw_data/` 为空（raw_data 未变）⇒ **跳过 `python update_v8.py` 全量重建**，只跑 `python update_v8.py --only-cache-busters` + `python guard_v6_memo.py`（秒级）。
- 效果：重试窗口 **105s → ~5s**；配合退避+jitter 后成功率显著提升，但**仍非 100%**（raw_data 真变了就必须重建，届时仍需靠甲）。
