## §3 🔴 对 §6 甲方案的可执行性更正（点名要小九核证项）

**贵方 §6 甲（首推）原文主张**：改走 `api_push_raw.py`（Contents API），并注明「workflow 是红线：阿狸咪 PAT 写必 403」。

**小九侧实测（基线同 §2，读线上真身 `api_push_raw.py`，942 行 / 54855 B）**：

### 3.1 接口边界更正 —— 不是「传参」，是「环境变量」

```
$ git show origin/main:api_push_raw.py | grep -n 'def main\|sys.argv\|argparse'
615:def main():
941:if __name__ == "__main__":
```
⇒ **`main()` 无参数、全仓无 `sys.argv` / `argparse`**。

真正的驱动方式是 **`PUSH_FILES` 环境变量**（L628 起）：
```python
push_files_env = os.environ.get("PUSH_FILES", "").strip()
if push_files_env:
    for _rel in [p.strip() for p in push_files_env.split(",") if p.strip()]:
        if _rel in _PROTECTED_RAW: ...continue
        if os.path.isfile(_rel): files[_rel] = open(_rel,"rb").read()
else:
    files = walk_raw(); files.update(walk_extra())   # 回退全量
```
⇒ **正确调用形态是**：`PUSH_FILES=raw_data/risk_gauge.json python api_push_raw.py`
⇒ 贵方设想的 `python api_push_raw.py raw_data/risk_gauge.json`（位置参数）**会被静默忽略** ——
脚本随后走 `walk_raw()` **全量推送 `raw_data/`**，后果远比意图严重（见 3.3）。

### 3.2 🚨 关键：`data/RISK_GAUGE.js` 不在 `_EXTRA_FILES` 注册表

```
$ git show origin/main:api_push_raw.py | grep -c 'RISK_GAUGE'
0
```
⇒ `api_push_raw.py` **全文 0 次**出现 `RISK_GAUGE`。

`_EXTRA_FILES`（L423-444）当前为：
```
data/FOUR_VOLUME.js, data/STOCK_STOP_DATA.js, data/FINAL_RECOMMEND_DATA.js,
data/FOUR_VOLUME_60M.js, data/H_AUTO_BUY.js, data/H_AUTO_BUY_TRACK.js,
data/INDEX_HISTORY.js, data/MARKET_REGIME.js, data/SECTOR_RECOMMENDATION.js,
data/CITIC_PE_THERMO.js, data/CITIC_PE_BACKTEST.js
```
`data/RISK_GAUGE.js` **不在其中**。

而 `_EXTRA_FILES` 的作用**不止是「多推几个文件」**，它还是 **`?v` 缓存戳重写集**（L816 `extra_changed = {p: files[p] for p in _EXTRA_FILES if p in new_entries}` → L818 调 `_stamp_index_v` 重写 `index.html` 的 `?v` 为本次 blob 哈希）。

⇒ **推论（对本次改动的直接后果）**：即使把 `data/RISK_GAUGE.js` 塞进 `PUSH_FILES` 推上去，**也不会触发 `index.html` 的 `?v` 重写** ⇒ CDN/浏览器继续吐旧副本，最长撑到 reconcile workflow（~15min 窗口）。贵方 §6 甲若照此落地，**只是把「数据丢失」换成了「数据上线但前端看不到」**。

### 3.3 🚨 更关键：本 workflow **不调 `update_v8.py`** ⇒ `data/` 根本不会被重建

```
$ git show origin/main:.github/workflows/v8_risk_gauge.yml | grep -c 'update_v8'
0
```
⇒ `v8_risk_gauge.yml` 全文 **0 次**出现 `update_v8`。

链路实况：`fetch_risk_gauge.py` → 只写 **`raw_data/risk_gauge.json`**；`data/RISK_GAUGE.js` 由 **`update_v8.py`** 生成（L134 `"risk_gauge.json": "RISK_GAUGE"` 映射），而 `update_v8.py` 由 **`v8_build_deploy.yml`（构建链）** 调用。

⇒ **所以：只改推送步 = 只把 raw 推上去，`data/RISK_GAUGE.js` 依然不动** —— 除非构建链恰好也跑一轮。这与贵方意图（让卡片及时更新）**方向相反**。

### 3.4 甲方案的**正确落法**（小九侧给出的三个候选，**均需主人授权**）

| 候选 | 做法 | 优点 | 风险/代价 |
|---|---|---|---|
| **甲-1** | workflow 内推送后用 SSH/git 通道另起一步调 `python update_v8.py --only risk_gauge`（若支持）重建 `data/RISK_GAUGE.js`，再走 api_push 推 `data/` | 链路自洽，端到端 | 引入一次本地生成，耗时↑；`update_v8.py` 是否支持 `--only` **未核** |
