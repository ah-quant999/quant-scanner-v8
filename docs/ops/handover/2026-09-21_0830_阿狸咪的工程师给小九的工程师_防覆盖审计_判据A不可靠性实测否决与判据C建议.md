## 三、防覆盖正面证据（可复现）

### 3.1 本地独有项数 = 0

```
$ git rev-list --count FETCH_HEAD..HEAD
0                                        ← 无本地独有提交（判无损硬指标）
$ git rev-list --count HEAD..FETCH_HEAD
4                                        ← HEAD 落后远端 4 提交
$ git status --porcelain
(空)                                     ← ⚠️ 假象！
$ git diff FETCH_HEAD --stat
16 files changed, 132 insertions(+), 304 deletions(-)
```

**🔴 铁律实证：`git status` 会静默撒谎。** status 输出空（"自认为"干净），但
`git diff FETCH_HEAD` 显示 16 文件差异 —— 因 HEAD 落后，status 拿**旧 HEAD** 当基线。
⇒ **判防覆盖禁用 `git status`，必用 `git diff FETCH_HEAD --raw`**。

### 3.2 16 文件差异逐项定性

| 文件 | 差异性质 | 判定 |
|---|---|---|
| `index.html` | 唯一实质差异：**同一处口径行**（本地=标题下方；远端=两卡右侧第 3 列） | 远端更新，本地**不得推** |
| `calendar.html` | blob 差异是 **CRLF 假象** —— `hash-object`（带过滤器）得 `b1c7bc88` = 远端一致 | **实为一致** |
| `data/*.js`（12 个） | **同字节数纯时间戳推进**（本地 06:22 → 远端 06:48） | 仅慢一轮 |
| `raw_data/risk_gauge.json` | 数据推进 | 落后 |
| 你的交接件（新增 md） | `git cat-file -e HEAD:<path>` ⇒ **不存在于 HEAD** = 远端新增 | 正常新增 |

> ⚠️ **给双机一条新判据**：`git hash-object --no-filters <f>` 在 `core.autocrlf=true`
> 下会算出**不同** hash（CRLF 版），**不能**直接与 `git rev-parse <ref>:<path>` 比。
> 必须用 `git hash-object <f>`（带过滤器，规范化 CRLF→LF）。本轮我差点把它误判成
> 「calendar.html 被改动」。

## 五、🔴 核心纠正：你的「判据 A」实测**不可靠**，建议否决

### 5.1 你的原提案

```
prev_max = max(?v in 上一版 index.html)
cur_max  = max(?v in 本版 index.html)
cur_max < prev_max  ⇒  FAIL：「缓存令牌倒退 N 秒 ⇒ 疑似旧树覆盖」
```

### 5.2 为什么它会失效

`?v` **不是「提交时写死」的常量**，而是被一个独立 workflow **持续刷新**：

```yaml
# v8_cache_buster_reconcile.yml
on:
  push:  paths: [data/**, raw_data/**]
  schedule:  - cron: '*/15 * * * *'      # ← 每 15 分钟
# 动作：git fetch + reset --hard origin/main → python update_v8.py --only-cache-busters
# ⇒ ?v = 该时刻的 unix 秒，每次 reconcile 都刷新到「当下」
```

### 5.3 实测数据（我在本机对三个版本取 max `?v`）

| 版本 | max `?v` | 时刻 |
|---|---|---|
| 本地旧树（落后 4 提交、内容**确已改动**） | `1789943937` | 06:38:57 |
| 远端新树 | `1789946656` | 07:24:16 |
| **若落后机器跑了 reconcile** | **≈`1789949307`** | **07:57+（当下）** |

⇒ **落后树推送时，`?v` 反而比远端更新**（reconcile 把它刷成当下时刻）。
判据 A 会输出「正常」，**完全失效**。

> 你交接件里那句「本轮实测有效：`1789944528` vs `1789943937` ⇒ 倒退 591 秒」只成立于
> **两台机器都恰好没跑 reconcile** 的窄窗口。而 `?v` 每 15 分钟必刷 ⇒ 真实覆盖场景下
> 大概率不成立。**这正是「单点取证不可当判据」的又一例。**

### 5.4 附：`?v` 口径的唯一权威

```
# scripts/reconcile_cache_busters.py（已停写，护栏）自述：
#   ?v 旧口径（sha1 内容哈希）已于 2026-09-10 主人令废除
#   （原因：数据回滚时哈希恰好等于旧版 ⇒ 浏览器永远吐旧数据）
#   现行权威 = 单调 unix 秒令牌，唯一实现 = update_v8.py::_data_file_update_time()
#   唯一正确调用方 = v8_cache_buster_reconcile.yml
```
