## 6 本轮沉淀判据（可复核）

**61. 🧨 「跨机/跨会话文档已写」≠「已送达」——回执前必须区分「已入 origin/main」与「本机在制未推送」**
本轮本机存在并发会话的 `docs/ops/handover/2026-09-15_1200_…_回执_1135单根因A已修…md`（224 行，`git status` = **`??` 未推送**），其正文已完整覆盖 f1 根因 A；而按 T 判据（只看 `origin/main`）它**不存在**。
⇒ 若无脑「按 T 补写」，会产出**与在制会话雷同的第二份回执**（重复劳动 + 方向打架，承判据 58）。
**正解**：`git status --porcelain` 里凡 `??` 或 ` M` 的 `docs/ops/handover/*.md` 一律**先读内容**，再决定「补位哪些留白」。

**62. ✅ 判「WT 是纯落后 还是 本机独有改动」的最强单点判据：`GET /git/blobs/<full-sha>` 是否 200**
本仓是**浅克隆**（`.git/shallow` 边界持续漂移），`git log --all --find-object` 对真实历史 blob 会**静默返回 0 命中** ⇒ 产出**假「本机独有改动」**（承判据 9/54/55）。
而 GitHub 对象库是权威全集：**HTTP 200 ⇒ 该内容确曾入仓 ⇒ 纯落后，safe to `checkout`**；**404 ⇒ 从未入仓 ⇒ 禁 checkout**。
本轮 3 个文件（`build_unlisted_panel.py` / `v8_peer_monitor.py` / `v8_urgent_listener.py`）全部 200 ⇒ 一次性定性，**不再依赖任何本地历史反查**。

**63. 📏 「大文件推送失败」的诊断顺序（本轮新增）**
① 量尺寸 `git ls-tree -l <ref> <path>` → ② 算 base64 放大（× 4/3）→ ③ 与 GitHub blob API 的 **100 MB 请求体上限**比对 → ④ 再看 `api_push_raw.py` 的重试分类（落在「不可重试错误」里就**别加退避**，重试 8 次是纯浪费）。
本轮：76.08 MB → ≈101.4 MB ⇒ 必然 401。
**旁证铁律**：该类 `.py` 的 `.js` `update_time` 由 raw **透传** ⇒ **raw 推不上去 = 卡恒旧**，与「脚本跑没跑」无关（承判据 6）。

**64. 🔇 `##[error]` 不一定让 run 变红 —— 反之「run 全绿」也不能证明「数据都上去了」**
本轮 `raw_data/backtest_tdx.json 本轮上传失败，线上保留旧版本` 以 `##[error]` 打印，但 run `#1846` 结论仍是 **success**。
