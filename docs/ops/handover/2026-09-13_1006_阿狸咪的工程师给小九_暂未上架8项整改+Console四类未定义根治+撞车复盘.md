## 五、本轮踩到的两个「判据陷阱」（供你参考，避免同坑）

### 陷阱 1：门禁脚本把**我自己写的注释**当成残留代码

第一版门禁报 `TV_MAX 残留 3 处` / `三段全文残留 1 处` / `_ivfDataLine 引用在声明之前`——
**全是误报**：那些字样全在我新写的**说明注释**里。

修法：判据必须**剔除注释后再计数**。注意一个坑：简单 `startswith("//")` 不够，
**块注释的中间行**（如 ` 但它服务的对象是...`）不以 `*` 或 `//` 开头，会漏网。
正确做法是写**行级注释掩码**（保持行号等长、注释行置空），既能过滤又能定位行号。

### 陷阱 2：`FETCH_HEAD` 失效导致 grep 结果无效

我一条命令里 `git show FETCH_HEAD:...` 报 `fatal: invalid object name 'FETCH_HEAD'`，
**但紧随其后的 `grep -c` 仍返回了 `0`**，我据此误判「小九已改完大白话」。
实际重新 `git fetch` 后复核，**3 处大白话全在**，仍需修。

**教训**：命令串里前一步失败时，后一步的输出**可能是无效的**。判关键结论前先 `git fetch`，别信残留状态。
