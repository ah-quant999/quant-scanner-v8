## 二、命名规范：**时间优先**

```
YYYY-MM-DD_HHmm[_URGENT]_<发件>给<收件>_<主题>.md
```

**实例**

```
2026-09-10_2130_URGENT_阿狸咪给小九_派发源精简与假成功根治.md
2026-09-10_2200_阿狸咪给小九_补充审计+清理+三处缓存戳互踩.md
2026-09-11_0900_小九给阿狸咪_收盘数据核验回执.md
```

**规则**

| 段 | 取值 | 说明 |
|---|---|---|
| `YYYY-MM-DD` | 签发日期（北京时间） | 必须 |
| `HHmm` | 签发时刻，24 小时制、分钟级 | 必须。**读不到真实时间就写 `0000`，不许猜** |
| `URGENT` | 紧急件标记（可省） | 放在时间后，仍可按时间排序，又能一眼识别 |
| `<发件>给<收件>` | `阿狸咪的工程师给小九` / `小九给阿狸咪的工程师` | 双机双向，**署名见下节** |
| `<主题>` | 简明中文 | 不要含 `?` `*` `:` `/`（Windows 非法字符） |

## 三、为什么按文件名排序，而不是按修改时间

- **`ls` 默认排序 = 文件名排序 = 时间排序**，无需任何额外操作。
- **绝不能用 mtime**：本仓库被坚果云实时同步，同步会**重写 mtime** →
  历史上读取器按 mtime 取"最新交接"取错过，这才是真正的隐患（读取器已改）。
- 每台机器有**两个专家会话并发**处理不同事务，签发时刻带分钟就足以区分
  「谁在什么时间做了什么」，时间差本身就是判别依据。

## 八、🔴 并发避让协议（同机双专家 / 双机，2026-09-13 主人提问后定稿）

**背景（已核实）**：每台机上有**两个专家会话并发**改同一个仓库，且双机共用同一
GitHub 账号 `ah-quant999` + 同一 email ⇒ **commit author 完全相同**。
⇒ 「谁改的」在 git 层**原本不可区分**，同机两会话更无从区分。

### 8.1 怎么「区分」

| 维度 | 手段 |
|---|---|
| 哪一次改动 | 交接单文件名带 `HHmm`（分钟级）⇒ 时刻即区分依据（本目录既有规范） |
| 哪一台机 | commit message 末尾**自动**附 `[<hostname>]`（阿狸咪=家机 / 小九=单位机） |
| 同机哪个会话 | commit message 自动附 `[<hostname>/<会话号>]`；会话号由 **`v8_session.py id`**（唯一真源）按**会话目录**派生 （`V8_SESSION` 可显式覆盖）—— 见 8.5.1；取不到才只留机器名，**不许编造** |
| 谁在改什么 | commit message **必须写清主题**（如「回测口径」/「前端UI」）；另一会话据此判断是否与自己相关 |

> 上面两条 `[...]` 后缀由推送工具自动追加（本机 `atomic_patch_push.py`），
> 人工只需把主题写清楚。

### 8.2 怎么「避让」（按执行顺序，缺一即可能覆盖对方）

1. **推前必 `git fetch`**，基底一律从 `FETCH_HEAD` 派生。🔴 **禁止**直接用本机工作树
   当基底 —— 本仓被坚果云实时同步且工作树长期落后远端，用工作树 = 用陈旧内容覆盖别人。
2. **改动必须带锚点唯一性断言**：替换锚点命中数 **≠ 1 立即中止**。
   ⇒ 别人改过同一处时**必报错**，**绝不静默覆盖**。这是防覆盖的第一道也是最重要一道闸。
3. **push 必须用 `sha:refs/heads/main` 快进推**（禁止 `--force`）。
   ⇒ 被抢先时远端**拒绝**，对方的提交原样保留（**不会丢改动**）。
4. **push 失败 = 被抢先，不要盲目重试同一 sha** —— 该 sha 的 parent 已不是 main tip，
   重推永远不会成功。正确做法：**重取 base → 重做补丁 → 再推**。
   （本机 `atomic_patch_push.py` 已内置：识别 `non-fast-forward` 后自动重跑全流程，最多 3 轮。）
5. **改热点文件前先看它最近 10 分钟有没有别人提交**：
   `git log -3 --pretty='%h %ad %an %s' --date=format:'%m-%d %H:%M' <ref> -- <file>`
   热点清单：`index.html`、`logic.html`、`.github/scripts/*`、`.github/workflows/*`、`raw_data/*.json`。
6. **同机两会话按主题分区**：两个专家各管一摊（例：A 管前端/UI，B 管算法/数据），
   并在 commit message 写清主题 —— **同主题撞车概率远高于不同主题**。

### 8.3 🔴 禁止清单

- 禁 `git push --force` / `--force-with-lease`（会真覆盖对方提交）
- 禁 `git rebase -X theirs`（把对方的改动整段丢弃）
- 禁 `git add -A`（本仓被坚果云同步，历史事故：`data/` 101 文件被提交删除）
- 禁在仓库内留 `.bak`（会被同步层当主版本，反向回滚一切改动）

### 8.4 撞车后的处置

若锚点断言报错（说明对方已改同一处）：**不要**绕过断言硬改。
正确顺序：`git show <ref>:<file>` 看对方**改成了什么** → 判断自己的改动是否仍然必要 →
必要时把锚点更新为对方的新文本 → 重做补丁。**看不懂就先在同一目录发一份交接单问对方**。

### 8.5 🆕 同机双会话「结论登记器」（2026-09-13 落地，补 8.1–8.4 的空白）

8.1–8.4 防的是**字节级覆盖**（硬冲突）。本轮实测暴露**第二类事故：语义撞车** ——
同一个「backfill 回填」误判，在本机**两个会话里各发生一次**：

#### 8.5.1 🔴 身份派生重修（2026-09-13 实测缺陷，修于 `b6c2de0f1`）
