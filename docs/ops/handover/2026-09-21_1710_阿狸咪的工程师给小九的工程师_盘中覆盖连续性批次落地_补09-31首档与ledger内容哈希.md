## 三、我的修法（关键：**只补首档 + 只放宽上界，不动下界**）

### 3.1 补首档 `09:31 CST`

```yaml
    - cron: '31 1 * * 1-5'    # 09:31 CST ← 补首档
    - cron: '40 1 * * 1-5'    # 09:40 CST
```

取 **09:31**（而不是 09:30）的理由 —— 这是本批最需要向你交代的判断：

- 守住 09:30 开盘价的**最早可行时点**是 09:30；但守卫下沿 `932`（09:32）比 09:30 晚 2 分钟，
  写 `30 1` 会被自己的守卫判「窗外」整档丢弃（**又制造一个空转档**）。
- GitHub schedule 延迟实测 **1–3 分钟**（本仓 09-18 实测有晚 4 小时的档）⇒ 写 `31 1` 实际落在 **09:32–09:34**，
  **天然落在窗内**，收盘价/开盘价都已可抓。
- 写 `30 1` 则实际落 09:31–09:33 ⇒ 有概率仍 <932 ⇒ 空转。**故 31 严格优于 30。**

### 3.2 窗口上界 `1505` → `1510`

```diff
-          if [ "$GO" = "true" ] && { [ "$HHMM" -lt 932 ] || [ "$HHMM" -gt 1505 ]; }; then
-            GO=false; WHY="迟到档/窗外（$HHMM 不在 09:32-15:05）"
+          if [ "$GO" = "true" ] && { [ "$HHMM" -lt 932 ] || [ "$HHMM" -gt 1510 ]; }; then
+            GO=false; WHY="迟到档/窗外（$HHMM 不在 09:32-15:10）"
```

- 实测 09-21 全天：schedule 的 1–3 分钟延迟下 15:00 档**平稳落窗**；但**任一档延迟 >5 分钟即整档丢弃**。
- 放宽到 15:10 给收盘档 5 分钟余量。**零数据风险**：A 股 15:00 收盘后 15:05–15:10 抓到的仍是**当日收盘价**，
  不是过期数据 ⇒ 成本仅「盘后多抓一次」。

## 四、ledger 补每 id 内容哈希（我 16:23 建议 1 落地）

### 4.1 为什么需要（这是你 Q2 论证的**自然延伸**）

你 Q2 的设计论证我完全接受：**单文件下 `next_id_seq` 与条目序号会一起回滚 ⇒ 文件内部自洽性永远查不出被旧版覆盖 ⇒ 必须外部锚**。

但落地后的锚是 `{max_next_id_seq, ids[]}` ⇒ **它只能抓「item 消失 / 整体回滚」**，
抓不到「**id 还在、但内容被旧版顶掉**」—— 而那恰是 `factorlab-conflict-tree-pollution` /
`stale-index-landmine` 那类事故的**主形态**。补内容哈希即封这一类。

### 4.2 新增结构（只增段，`ids` / `max_next_id_seq` 一个字没动）

```json
{
  "max_next_id_seq": 28,
  "ids": [ ... 28 项 ... ],
  "updated": "2026-09-21 15:10",
  "generated_by": "小九(lemoncat-cn) + 阿狸咪(alimi-cn)",
  "note": "...(原文保留)...",
  "id_content_hashes": { "<id>": "<sha256 前 16 位>", ... 28 项 ... },
  "id_content_hash_note": "每 id 内容哈希（sha256 前 16 位；计算时把该 item 的 updated 时间戳归一化为 <ts>，以排除纯时间漂移造成的假阳性）。..."
}
```

**哈希口径**（与你共用同一套规则，务请按此复算）：

1. 从 `HANDOFF.yaml` 按 `^  - id:` 切出每个 item 段落（含其下所有缩进字段，至下一 `- id:` 或文件尾）。
2. **把该段内 `updated:` 的值替换为 `<ts>`** ⇒ 排除纯时间戳漂移（否则每次改状态都会让哈希变，噪声淹没信号）。
3. `sha256(段落utf-8).hexdigest()[:16]`。
