## 二、根因（三层，第 3 层才是真教训）

### 2.1 直接原因
我的推送器 `api_push_paths.py` 以**二进制读工作树**（`loc.read_bytes()`）直推 Git Data API
⇒ **完整绕过 `.gitattributes` 的 `text eol=lf`** ⇒ 工作树的 CRLF 原样进 blob。
而我**刚用 `--renormalize` 把 blob 变成 LF**，一推就被自己**当场作废**。

### 2.2 为什么是「永久脏」而不是「暂时脏」
判据是**三元组**（与我上一条交接件 §1.1 的纠正同源）：

```
i/crlf   ∧   attr 含 eol=lf   ∧   w/crlf     ⇒ 结构性不等，永不可能收敛
```

blob=CRLF、属性要 LF ⇒ `clean(worktree)` 恒为 LF ≠ 库中 CRLF ⇒ `git status` **恒脏**。

### 2.3 🔴 真教训（第三层，请重点看）

**这条铁律我早就写进记忆与技能了**：

> API 直推绕过 `.gitattributes` ⇒ 写侧 `newline="\n"` / 推边界 `fold_eol`

**但我以为「把 `.gitattributes` 补上规则 + `--renormalize`」就完事了，没想到我用的推送工具本身就在绕过它。**
⇒ **可复用的判据**：

> 凡走 **Git Data / Contents API 直推**的工具，**必须自带推边界行尾收口**；
> 「改了 `.gitattributes`」**不等于**「推上去的内容就是 LF」——
> 属性只在 **git 自己 add/checkout** 时生效，**API 直推路径上它完全不参与**。
> 排查时**先问：这条推送路径经过 git 的属性过滤吗？**

## 三、修法（两处，均已落地）

### 3.1 推送器补 `fold_eol()`（核心修复）

```python
def fold_eol(rem, data):
    """按 .gitattributes 把**待推内容**归一为 LF；返回 (新内容, 是否折叠)。"""
    m = _norm_module()                      # 复用仓库内 scripts/normalize_eol.py
    if m is None: return data, False
    exp, _how = m.expected_lf(REPO_DIR, [rem])
    if not exp.get(rem): return data, False  # 非 eol=lf 路径不碰
    new = m.to_lf(data)
    return new, (new != data)
```

**为什么复用 `normalize_eol.py` 而不是另写规则表**：它的判定走 `git check-attr`
（与 `.gitattributes` **同源**）；另写一套必然随属性演进而**漂移**
——这正是本项目「两套口径必漂移」的历史教训。

**实测**：4 个目标文件 `folded=True`（CR→0）；**`logic.html` `folded=False`**（有意 CRLF，自动跳过，未误伤）。

### 3.2 顺手修掉一个**会造成假警报**的校验 bug

原 `[6/6]` 推后回读校验比的是 **`loc.read_bytes()`（工作树原样）**，
而上传时内容已折叠为 LF ⇒ **凡 `eol=lf` 文件必然误报「逐字节不符」**。
本轮实证：修 4 个文件时 `❌ 0/4 逐字节一致`，**但用 `git cat-file` 核对远端 blob CR 全为 0，证明推送本身完全正确**。
**已修为比「折叠后」的内容。**
⇒ **判据**：校验器的**比较基准必须与上传基准一致**，否则「工具报红」与「事实正确」会长期背离，
久了一定会有人在真红时当成假红。
