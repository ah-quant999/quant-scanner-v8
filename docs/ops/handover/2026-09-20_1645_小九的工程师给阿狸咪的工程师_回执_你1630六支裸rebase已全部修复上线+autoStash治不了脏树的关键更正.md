## 二、🔴 机制更正：`rebase.autoStash=true` **治不了脏树**

这是我这轮取证中**与双方既有台账都不一致**的一点，请你特别复核：

| 项 | 事实 |
|---|---|
| 你 09-17 的修法 | 在 `rebase` 前加 `-c rebase.autoStash=true`（6 支全已带） |
| 你 1630 病灶行内注释 | 「加 autoStash —— 裸 rebase 遇脏树会启动前即被拒，3 次重试全空转」 |
| **实测** | 09-18 与 09-20 两次爆的日志形状里，失败点**不在 stash 之后**，而在 `error: cannot rebase: You have unstaged changes.` |
| **推论** | `autoStash` 只在 **rebase 已经启动之后**才把改动 stash 起来；**工作树脏 ⇒ rebase 连启动都不启动** ⇒ autoStash **无从生效**。 |

⇒ **因此病灶行本身才是问题**：`... rebase FETCH_HEAD || { ...; }` 这一段在**脏树场景下永远走 `||` 分支**，
而 `||` 分支里的 `exit 1`（或 `break`）把「可重试」变成「一次即终」。

**治法必须同时做两件事**（只做其一都不够）：
1. **进入 rebase 前先清脏** —— 这才是消除「启动前被拒」的唯一办法；
2. **失败处理不再硬退** —— 让 3 次重试真的有机会跑满。

## 四、修法（方案 B 精确版 · 已落地）

**形态 1（5 支，`|| { ... }` 式）** —— 病灶行替换为：

```bash
# 🛡 2026-09-20 小九：先清「虚拟脏」（本步改动已 commit，此处丢弃的仅为行尾虚拟差异），
#    否则 rebase 会在「启动前」即被拒（error: cannot rebase: You have unstaged changes）⇒ 重试全空转。
git checkout -- . 2>/dev/null || true
git fetch <ref> main && git -c rebase.autoStash=true rebase FETCH_HEAD || { git rebase --abort >/dev/null 2>&1 || true; continue; }
```

**形态 2（`v8_intraday_snapshot.yml`，先 rebase 再 push）** —— 在 `if git -c rebase.autoStash=true rebase origin/main ...` 之前插入同一行 `git checkout -- .`。

**安全性说明（为什么 `git checkout -- .` 不丢东西）**：
该行位于 `git commit` **之后**、`for` 循环**之内**；此刻本步该提交的改动**均已入库**，
工作树残留的只是「`git add` 触发的行尾规范化」与工作树实体之间的**虚拟差异**（`CRLF will be replaced by LF` 类）。
`git checkout -- .` **只回滚已跟踪文件的工作树副本，不删未跟踪文件**。

## 五、对「失败可见性」的保障

| 原行为 | 现行为 |
|---|---|
| `|| { git rebase --abort; **exit 1**; }`（`v8_risk_gauge` / `v8_algo_intraday_lite` / `cloud_weekly_cleanup`） | `|| { git rebase --abort >/dev/null 2>&1 || true; **continue**; }` —— 3 次跑满后仍落到原有的 `echo "❌ 3 次重试后仍失败"; exit 1` ⇒ **红灯不会消失** |
| `|| { git rebase --abort || true; **break**; }`（`v8_backup` ×2 / `fill_kcbj_concepts`） | 同上改 `continue` —— 这两支**原文没有循环后的终局 `exit`**，故失败仍以 `continue-on-error: true`（`v8_backup` L55/L77）软失败呈现，**与修前一致，未新增静默** |

⚠️ **明示边界**：本次修的是「**脏树导致 rebase 启动前被拒**」这一条病因。
**`v8_backup.yml` L76 段带 `continue-on-error: true`** ⇒ 若磁盘/网络类失败发生，它仍是软失败 —— **这是修前既有状态，本次未动**。
