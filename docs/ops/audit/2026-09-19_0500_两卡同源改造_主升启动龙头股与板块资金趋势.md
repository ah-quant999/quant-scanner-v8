## 3 根因（三层，每层均有实证）

### 3.1 层一：两卡各有一套判定与两个时点（直接原因）

| | 图 2 板块资金趋势 | 图 1 主升/启动 板块·龙头股 |
|---|---|---|
| 判定位置 | `index.html` 函数内联（`if (d5>3 && d20>5)`） | `scripts/fetch_sector_leaders.py::_phase_of`（生成期） |
| 数据 | `window.SECTOR_RS`（实时读） | `window.SECTOR_LEADERS.sectors[].phase`（**快照**） |
| 刷新 | 每次页面加载现算 | 只随生成器跑动 |

⇒ 只要两者不同步，必然不一致。

### 3.2 层二：SECTOR_LEADERS 未接自动链（放大原因）

`data/SECTOR_LEADERS.js` 的提交史（实取）：

| 提交 | 时间 | 作者 |
|---|---|---|
| `dedeebbd7c` | 09-18 20:12 | ah-quant999（**手动**） |
| `082b496c8e` | 09-18 18:12 | github-actions[bot] |

而 `data/SECTOR_RS.js`（同窗口）：

| 提交 | 时间 |
|---|---|
| `b742045cd0` | **09-19 00:46** |
| `6be697367f` | 09-18 21:55 |
| `a233291629` | 09-18 20:59 |
| `38ad0e33f7` | 09-18 20:33 |
| `db2b134dbf` | 09-18 20:01 |

⇒ **RS 每 20 分~1 小时被 cn fetch 刷新一次，龙头字典靠手动推** —— 两卡数据版本相差 5 小时（19:55 vs 00:41）。

### 3.3 层三：生成器静默丢板块（数量差的直接原因）

`scripts/fetch_sector_leaders.py` 旧版：

```python
bk = boards_exact.get(nm) or boards_norm.get(_norm(nm))
if not bk:
    log("skip(no-match-even-norm): ...")
    continue          # ← 静默丢弃整板块，前端无任何提示
```

实测（用真 SECTOR_RS 跑真匹配逻辑）：

| 项 | 数 |
|---|---|
| RS 中主升+启动板块 | **42** |
| 名字能匹配东财板块 | **39** |

| 产物实际输出 | **9**（其余 33 个因名称归一失败被丢） |

> 注：42→9 的直接原因不是这 3 个匹配失败，而是**生成时刻（09-18 19:55）RS 还只有 9 个主升+启动板块**（见 §5）。静默丢弃是另一个独立缺陷（会吃掉 3 个）。

## 4 修法：单一真源（不是"对齐两套数据"）

### 4.1 设计原则

**判定与数值只允许有一个来源 = `window.SECTOR_RS`；`SECTOR_LEADERS` 降级为「板块名 → 龙头股」字典，不再决定板块清单与阶段。**

这样两卡同源，**几何上不可能不一致**（同一个数组 + 同一个函数），而不是靠"记得把两份数据同步"。

### 4.2 改动清单（`fcc24a6dd6`）

| 文件 | 改动 |
|---|---|
| `index.html` | ① 新增模块级唯一判定 `__PHASE_RULE_VER` / `__PHASE_META` / `__PHASE_ORDER` / `__phaseOfSec`；② 图 2 删内联判定改调 `__phaseOfSec`；③ 图 1 `_fillSectorLeaders` 重写：板块清单+phase+5日/20日涨幅全部现算自 `SECTOR_RS`，`SECTOR_LEADERS` 仅作字典；④ 主升展开/启动折叠（对齐图 2「点击查看」）；⑤ 无龙头股时按 `no_match` / `leaders_error` / 未覆盖 三种原因明示；⑥ 卡底加「口径对账」行；⑦ 加 600ms×30 自愈轮询（覆盖 defer 加载窗口） |

### 4.3 别名表（人工确认，非猜测）

```python
MANUAL_ALIAS = {
    "塑料制品": "塑料",           # 申万二级「塑料制品」↔ 东财「塑料」
    "橡胶制品": "橡胶",           # ↔ 东财「橡胶」
    "汽车服务及其他": "汽车服务",   # ↔ 东财「汽车服务」
}
```

命中别名时产物标记 `match="alias:*"`，可审计追溯。**未做任何"相似度模糊匹配"** —— 那会把"张冠李戴"变成静默的错。

## 5 🔴 上游隐患（已定位、未修改，需决策）

### 5.1 现象：SECTOR_RS 在同一交易日内数值剧烈跳变

同一份 `data/SECTOR_RS.js`，09-18 同一天内的两个版本：

| 版本 | update_time | 主升 | 启动 | 退潮 |
|---|---|---|---|---|
| `db2b134dbf` | 09-18 **19:51** | 1 | 8 | 55 |
| `6be697367f` | 09-18 **21:43** | **3** | **39** | 12 |
| `b742045cd0` | 09-19 00:41 | 3 | 39 | 12 |

90 个板块中 **86 个（96%）5 日涨幅漂移 > 1 个百分点**：

| 板块 | 19:51 版 | 21:43 版 | 差 |
|---|---|---|---|
| 半导体 | 4.30 | 11.05 | **+6.75** |
| 多元金融 | −6.20 | −0.16 | +6.04 |
| 生物制品 | 0.69 | 6.35 | +5.66 |
| 医疗服务 | 3.45 | 9.10 | +5.65 |
| 房地产 | −2.95 | 2.28 | +5.23 |
| 工业金属 | −5.87 | −0.65 | +5.22 |

**方向高度一致（普遍 +5pp 左右的正向偏移）**，特征符合「窗口整体错开一个交易日」或「同花顺 EOD 未落地时拿到上一交易日 K 线」。两者 `source` 字段**都写"同花顺"**，故不是主/备路径切换。

### 5.2 相关代码缺陷：`data_date` 用的是「生成日」而非「交易日」

```python
# algorithms/fetch_sector_rs.py
result = {"update_time": now_str, "data_date": now_str[:10], ...}   # ← now_str[:10]
```

后果（实测）：
- 09-19（周六）产出的文件里 `data_date = 2026-09-19` —— **周六被写成交易日**
- 19:51 那轮承载的是 09-17 的 K 线，却标 `data_date = 2026-09-18` ⇒ **陈旧数据被标记成当日，无法自证**
- 该 `data_date` 同时用作 `SECTOR_PHASE_HISTORY` 快照的 `date` 键 ⇒ 「阶段迁移」会多出/错位快照

### 5.3 影响与建议（未擅自动手）

| 影响面 | 说明 |
|---|---|
| 前端两卡 | 已免疫（同源）——数值怎么变，两卡一起变 ✅ |
| 信号可信度 | ⚠️ 若某个自动化时点（如 20:00 盘后批）读到 19:51 版，会基于**上一交易日**的数据判阶段 |
| 阶段迁移统计 | ⚠️ 快照 `date` 键可能错位 |

**建议**：把 `data_date` 改为「同花顺返回的最后一根 K 线日期」（众数，防个别板块数据缺失），并在**前端与产物**里显式展示该日期。这样陈旧轮次会自证「数据基于 09-17」，而不会伪装成当日。

**未擅自修改的理由**：该字段是 `_save_phase_snapshot()` 的键、`v8_verify_layer_parity.py` 的比对锚点（`index.html` 注释原文：「2026-08-18 补：板块周期卡比对锚点」），改语义会影响 parity 校验与迁移统计，属**跨层语义变更**，宜先决策再动。
