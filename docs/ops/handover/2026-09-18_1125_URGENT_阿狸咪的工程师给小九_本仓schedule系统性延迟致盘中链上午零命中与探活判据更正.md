### 乙｜结构性·最彻底：**盘中链改「单点触发 + 链尾自接力」**

本仓已有**当日实证的成功范式**：`v8_cn_fetch_cloud.yml` 今日 **10:04–10:58 连续 9 档 success，全部为 `workflow_dispatch`**，
节拍稳定 5–8 分钟，**完全不依赖 schedule** —— 因为它靠**链尾 relay 自派下一档**。
把 `intraday_snapshot` / `algo_intraday_lite` / `lemoncat` 改成同样形态：**首档由 1 次外部触发（或 1 次 schedule 命中）启动，其后每档尾部 relay 自派下一档** ⇒ schedule 只要命中 **1 档**即可自持全天。

🛑 **硬边界（务必遵守）**：
1. 自接力链必须用**独立 `concurrency` 组名**，**禁复用 `v8-cn-fetch-cloud`**（09-10 跨链互顶 pending 教训）；
2. 自接力**必须带收盘截止 + TTL**（越过 15:00 即停，禁夜间自持，防跑成第二条 `cn_fetch` 那样的 24h 节拍源）；
3. **不要**因为「schedule 不灵」就给每条链各加一个派发源 —— 那是 09-10「多源互顶 pending → 大量 cancelled」的原路。

### 丙｜兜底：贵方 §1.4 的「盘中链首跑探活」自动化 —— **判据要改**

贵方原判据「09:15 检查今日 run 数，为 0 则告警 + 自动 dispatch」**在本仓会假绿/假红**，因为 §2 已证「当日 run 数」受延迟污染（09-17 中午前为 0，晚间却出现 5 档）。
建议判据改为**窗口化应到/实到**：

```
对每条盘中链：
  应到 = 当前时刻往回 30 分钟窗口内、被该链 cron 覆盖的档数
  实到 = 同窗口内该链 created 的 run 数（含 schedule + dispatch）
  若 实到 < 应到 且 距上次实到 > 2×节拍 ⇒ 告警
补派限制：每链每轮最多 dispatch 1 次 + 10 分钟冷却 + 当日累计上限（防自愈环）
且必须是【单一哨兵】统管全部链，禁每链各自派发
```

§2.1 已证为**连续两日**同日同时段零命中 ⇒ 属结构性，观察第二日不会给出新信息。
