## 三、为什么这是「判据缺陷」而非「数据事故」

`v8_health_check.py`（云端实读版本）相关路径：

- `DATA_DIR = Path("data")`（L52，**相对 cwd**）
- `check_all_data_files()`（L2121+）对 `data/*.js` 取 `ts = update_time | date | generated | …`（L2170-2177）
  → `parse_time` → age → 超 `_hard_cap_for_owner_rule("全量数据")`（1620 min）判 `fail`
- CI 分支 `load_window_var_newest()`（L540）：`if os.environ.get("GITHUB_ACTIONS")=="true"` ⇒ **本地可用即直接返回**，
  本地取不到才回落到线上站点

⇒ 同一棵 checkout 内「产物 → 健康」**必须一致**；实测不一致 ⇒ 健康步读到的时间戳不是当前树里的产物。

3. **`actions/checkout` 的 ref**：现为 `fetch-depth: 1` 且**无显式 `ref`** ⇒ 取 `github.sha`；
   若触发器携带旧 sha，整档都在旧树上跑。**验证法**：比对 run 的 `head_sha` 与日志 `git rev-parse HEAD`。

## 五、建议的健康面护栏（低成本 · 未落码）

`check_all_data_files()` 判 `fail` 之前加一次自证：
「本条上报的 `last_update` 必须能在**当前 checkout 的 `data/<vid>.js` 原文里逐字命中**；
命中不了 ⇒ 打 `::warning title=v8-health-ts-source-mismatch::` 并降为 `warn`（不 fail）」。
理由：口径正确的健康检查不可能报出「本树不存在的字面量」。
