## 一、主人看到的现象与真实根因

主人截图显示看板页多张卡片挂红。取证结论：**盘前 08:24 快照 14 项 fail，其中 12 项是误报，只有 2 项是真故障。**

### 根因：多层阈值叠加，取严方向错误

`v8_health_check.py` 对「实时数据」等页面算有效阈值时是两路并联、最后 `min()` 取严：

| 层 | 函数 | 盘前 08:24 给出的值 | 是否合理 |
|---|---|---|---|
| 分时口径 | `adjust_max_age()` | 1221 min | ✅ 合理（距上一交易日 15:00 收盘的真实时长） |
| 主人红线硬帽 | `_hard_cap_for_owner_rule()` | **360 min** | ✅ 单独看合理（防「陈旧数据长期不报」） |
| 实际生效 | `min(1221, 360)` | **360 min** | ❌ **错** |

盘前 08:24 距昨日 15:00 收盘已 1221 分钟，而硬帽把阈值压到 360 分钟 ⇒ 凡是「按交易日产出、盘前尚未到点」的卡片**必然全红**。这不是某张卡的 bug，是**阈值口径本身缺一条不变量**——所以以前逐卡加白名单永远修不完（这正是「红一次修一次、下次换个卡再红」的机制）。

同类第二处：`IPO_DATA` 的 `max_age` 已按主人令改成 1440，却被 `adjust_max_age()` 的盘前分支 `min(1440, 180) = 180` 反手打回 180 分钟 → 照样误报。

### 治本方式：新增「合法空档下界」不变量（只放宽、绝不收紧）

在 `v8_health_check.py` 插入约 110 行，把旧实现整体改名为 `_adjust_max_age_legacy` / `_hard_cap_for_owner_rule_legacy`（**函数体一字未动**），外层包一层：

```
非活跃产出窗口内：阈值 = max(旧值, 距上一批应产出时点 + 180min 宽限)
活跃产出窗口内：完全沿用旧逻辑（严格阈值原样保留）
```

关键点：这是 `max()`，数学上**只能放宽、不可能收紧** ⇒ **结构上不可能制造新红灯**。

- `_REG_ACTIVE_WINDOW`：实时数据/今日事件 (09:30–15:00)、盘后数据/选股策略/全量数据 (20:30–24:00)
- `_REG_CYCLE_MARK`：今日事件 (09:15)、盘后类 (20:30)
- `_REG_GRACE_MIN = 180`：批次产出 + 构建部署 + CDN 回源的合理宽限
- 交易日判定统一走全仓唯一的 `_is_trading_day()`（含补班日），不再各处自己算

调用点（`_dual_threshold` / `_dual_hard_cap` / `check_data_cards` / `check_all_data_files`）**一处未改**，自动继承新不变量。

## 六、推送方式（防覆盖，供复核）

- 采用**隔离索引**：`GIT_INDEX_FILE=.git/tmp_push_idx` → `read-tree <远端真实 ref>` → 只 add 本批文件 → `write-tree` → `commit-tree -p <远端 ref>` → `push origin <C>:main`（**force:false**）。
- **绝不移动本地 HEAD、绝不动主 index**；收尾只删临时索引。
- 三重闸门：① 窗口守卫（盘中直接拒绝）② **防覆盖比对**（远端该文件 blob 若不等于改动基线 blob → 中止，不覆盖他人成果）③ **范围守卫**（`diff-tree` 结果必须恰为本批 8 项，多一个少一个即中止）。
- 推后核验：`git ls-remote` 确认远端 ref 指向新提交；`v8_build_deploy.yml` 自动触发构建部署。

## 九、11:50 追加修复：`v8_health_check.py` 的两处结构性假红（对齐阿狸咪 1135 URGENT 单 · 根因 A-1 / A-2）

### A-1｜CI 内 `local_sync` **必然**假红 → 已短路

**取证**（阿狸咪提供 + 本地复核）：`v8_health_patrol.yml` 是 `runs-on: ubuntu-latest` + `fetch-depth: 1` 的**一次性浅克隆**，
而生成器每几分钟推一次 main ⇒ 该克隆的 `HEAD` **必然 ≠ origin/main** ⇒ `check_local_head_sync()` 在 CI 内**必然 FAIL**
⇒ patrol 的「🔁 自愈验证」step 必然 `REMAIN_FAIL>0` ⇒ 整轮红 + 升级邮件
（近 72h 实测 **9/47 = 19% 假红**，跨 09-14 15:34 ~ 09-15 09:17 持续 ≥18h 未修）。

**修法**（`check_local_head_sync()` 函数开头，单点短路）：

```python
if os.environ.get("GITHUB_ACTIONS") == "true":
    return [{"id": "local_sync", "name": "本地与 origin/main 同步", "page": "管线",
             "status": "info", "message": "CI 环境（一次性浅克隆）内本项语义不成立，跳过"}]
```

本检查只在运维机（小九 / 阿狸咪本机）有意义，CI 内降级 `info`。

**实测**：模拟 `GITHUB_ACTIONS=true` 实调 → 返回 `status=info` ✅
