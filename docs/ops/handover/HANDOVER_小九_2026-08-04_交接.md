## 二、定时任务审计结论（今日重点）

用户原话：「云端盘中任务很多都没运行的感觉」。API 实测结果：**感觉是对的**。

| 任务 | 今日应跑 | 实际状况 | 关键问题 |
|---|---|---|---|
| 🇨🇳 v8_cn_fetch | 工作日 12 次 | 上午 08:25–11:00 多档缺失；11:30 后恢复，但均延迟 10–15 分钟 | GitHub schedule 触发不可靠 |
| 🌍 v8_risk_gauge | 工作日 17 次 | 仅 09:30、12:30 左右有成功运行 | 大量 slots 未触发；截图中 10Y 美债/北向资金 `--` 与此相关 |
| 🇨🇳 v8_algo_run | 18:30 / 20:00 | 今天尚未到点 | 昨天 schedule 18:30 失败，靠多次手动 dispatch 才在 07:42 跑完 |
| 🩺 v8_algo.yml 体检 | 09:00 / 17:00 | 09:00 档未触发，11:56 才跑（时间异常） | schedule 时间漂移 |
| ☁️ v8_backup | 21:00 | 昨天延迟 2.5h（23:36） | 经常性延迟 |
| 🛡️ v8_safety_net | 每 20 分检查 | 正常 | 兜底检查本身健康，但只能兜底「1 小时无成功」，补不回所有精确 slot |
| ☁️ v8_build_deploy | 触发式 | 多次成功 | 自动部署链健康 |

**根因判断**：GitHub Actions 的 `on.schedule` 触发器本身存在延迟/跳过（官方文档承认）。不是 runner 离线，而是调度器未准时派发。 safety_net 只能做粗粒度兜底，无法保证每个精确 slot。

**阿狸咪注意**：这个看板的数据是**静态快照**，不是实时 API。若用户后续要求「自动刷新」，需要：
1. 新增一个周期性 workflow/script，调用 GitHub API 拉取各 workflow runs；
2. 写入 `raw_data/workflow_runs.json`；
3. `update_v8.py` 映射为 `data/WORKFLOW_RUNS.js`；
4. 前端 `renderTaskSchedule` 改读 `window.WORKFLOW_RUNS`。目前先以上线静态看板为主。
