## 四、🔴 422 事故与根治（后人必读）

### 现象
首推（11:37，原脚本 `_fl_push3.py`）在**创建 commit** 步失败：

```
HTTP 422 {"message":"Invalid request.\n\nFor 'properties/message', [\"fix(ui): 清理因子实验室…
```

注意报错里 message 的**值以 `[` 开头** —— 那是 **JSON 数组**，不是字符串。

### 根因（AST 铁证）

原脚本：

```python
COMMIT_MSG = (
    "fix(ui): …\n"
    …
    "署名：阿狸咪的工程师",     # ← 这个尾逗号
)
```

**末尾逗号使 `COMMIT_MSG` 退化为 1 元组**（相邻字符串字面量先自动拼接为单个 `str`，
再被 `,` 变成 `tuple`）。`json.dumps({"message": ("…",)})` ⇒ `{"message": ["…"]}`
⇒ GitHub 要求 `string` ⇒ **422**。

AST 实证（脚本从未执行主体即可判定）：

```
原脚本: 节点=Tuple    | 值类型=tuple | len=1
副本  : 节点=Constant | 值类型=str   | len=734
```

### 修复与处置

- 在 `E:\WorkBuddy交付\_tools\_tmp\audit\_fl_push4.py`（**仓库外副本**）删掉该尾逗号；
  **未修改原脚本 `_fl_push3.py`**（遵守「不要修改脚本」）。
- **未强推、未 force**；422 发生在 create-commit 步，**当时 `refs/heads/main` 未被 PATCH，main 分文未动**。
- 重跑前**重新现取 tip**（`ef8cd1f5e44b`）—— 期间他人已推进 2 个提交，脚本「现取 tip」设计正确吸收。

## 五、两条新判据（入库备查）

### 判据 199｜`--dry` 通过 ≠ 能推送（**dry 盲区**）

原脚本 `--dry` 在**第 5 步校验后**即 `sys.exit(0)`，**从未执行第 6 步**（create blob/tree/commit/PATCH ref）。
⇒ 11:28 的 `--dry` 全绿，**掩盖了 message 侧的 422**。

**通则**：凡「dry 模式提前 return」的脚本，其 dry 通过**只覆盖 dry 之前的路径**。
上线前必须确认 dry 是否覆盖**全部写路径**；否则应补一次「最小真实写入」预演，
或对写入 payload 做**静态类型审查**。

### 判据 200｜JSON 化前断言关键字段类型

**尾逗号把 `str` 变 `tuple`** 是 Python 常见笔误，且**脚本自身不报错**，
只有对端 schema 校验才暴露。

**通则**：`POST` 前对关键字段 `assert isinstance(v, str)`。
另注：**GitHub 报错里值以 `[` 开头（数组） vs `"` 开头（字符串）是最直接的线索。**
