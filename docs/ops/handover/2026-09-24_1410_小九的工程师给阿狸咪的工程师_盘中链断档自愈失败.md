`数据未变，跳过重写（幂等）` 的真实含义是**本轮未取到新数据（抓取函数返回 None）**，而非「链路正常」。

### 2.3 自愈机制被自身「防重复派发」逻辑锁死

同一 run 日志：

```
[HEAL✓] [intraday] ETF 资金热度, 概念排名, 平均股价: 已有排队中的 cn_fetch 运行
        (created 2026-09-24T05:26:08Z)，跳过派发（避免顶掉该 pending run）category=intraday
```

即：13:26 起就有一个 pending 的 intraday run，此后**所有自愈源都因「已有排队中的 run」而跳过派发**。一旦队首 run 长期拿不到执行槽位，整条自愈链即**自锁**，且队列被看门狗/顶替机制批量清空后，又回到「重新派发 → 再次排队」的循环。

### 2.4 看门狗「破锁」可能误伤排队 run

`v8_cn_fetch_watchdog.yml` 注释明确写道：

```
释放 v8-cn-fetch-cloud concurrency 锁。否则一个卡死 run 占锁会把主派发档挡掉 → 数据空窗
[watchdog] 🔓 破锁：取消卡死 cloud run#{id}（龄{age}分，释放 concurrency）
```

14:06–14:07 的批量 cancel 与该看门狗 cron（`7,22,37,52`）时点吻合。**需人工确认：破锁判据是否把「正常排队（pending）」误判为「卡死」，从而在排队长时反而把队列全部清空、永不产出。**

3. **非僵尸假活**：全状态僵尸扫描无 in_progress 冻结 > 25 分钟的 run。

## 五、下一步建议

### P0（必须人工拍板）
1. **拆分并发组**：将 `intraday` 与 `post_close` 拆到**不同 concurrency group**（如 `v8-cn-fetch-cloud-intraday` / `...-postclose`）。当前二者共用 `v8-cn-fetch-cloud` 且串行，一次 post_close 长跑即可造成盘中整段空窗。
2. **复核看门狗破锁判据**：确认「龄 > N 分」的取消对象是否应只限 `in_progress` 假活 run；对 `pending`（排队中）run 不应 cancel，否则会反复清空队列。
3. **缩短单轮 post_close 时长**：`api_push_raw.py` 防倒退守卫逐文件下载远端 blob 比对是主要耗时源（raw_data 117 个 json / 26 MB）。建议改为**单次 tree 批量取时间戳**，把 46 分钟压到可接受区间。

### P1
4. **自愈派发去重**：dispatch 前先按 `category` 去重（同 category 已有 pending run 时不再派），避免 7 个同质 run 堆叠；同时保留一条「排队超时 → 升级告警」路径，避免静默自锁。
5. **断档真邮件告警**：当前断档仅以 `[FAIL]`/`[HEAL✓]` 形式留在 run 日志里，健康巡检与看门狗仍报 success ⇒ 主人盘中看到的仍是旧数据。建议 `update_time` 超阈值持续 > 40 分钟即触发真邮件。

### P2
6. 复盘「354533319 调度器 runs-on: ubuntu-latest 却是小九 self-hosted 主力」的命名与职责混淆，清理 workflow 名称与注释中的历史误导描述。
