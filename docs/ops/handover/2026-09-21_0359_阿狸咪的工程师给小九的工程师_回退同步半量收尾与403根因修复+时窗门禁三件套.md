### 2.2 真正的病根（四条，条条有实测铁证）

| # | 缺陷 | 铁证（run / 日志原文） |
|---|---|---|
| ① | **软预算结构性倒挂**：软预算 1080s **小于**实测耗时 1106~1293s ⇒ 每轮必半量收尾 | #1995：`⏱ 预算 1080s 用尽，本轮剩余 855 个文件跳过（已同步 438）` → `OK source sync done: 438/1293`；#1971：`387/1271` |

**另**：回退步采用 `if: steps.co.outcome == 'failure'` + checkout `continue-on-error` ⇒ **步骤 conclusion 恒 success，不可信**；
真判据是你用的「看耗时」——我复核 37 轮：**真跑 14 / skipped 23**，耗时分布 149~**1293s**（最坏 #1971），与你的 1106~1124s 同向。

### 2.3 修法（四层，逐层 sha1 自证；本机逐层单测实证）

| 层 | 机制 | 本机实测 |
|---|---|---|
| **A** | API blob + `Accept: raw` + `Accept-Encoding: gzip` + **keep-alive 单连接** | index.html **1,338,759 B → 460,868 B（2.9×）**；比旧「b64 优先」的 1,844,811 B **省 4.0×**；keep-alive 再加 **2.75×** |
| **B** | `raw.githubusercontent` + `Range` 分块续传（1 MiB/块），单块失败只重下该块 | HTTP **206**，2 块拼回 1,338,759 B，sha1 全等（本机 24.7s/1.28MB——慢但能下全；A 正常时用不到） |
| **C** | **urllib 兜底**（保留旧路径 + gzip）——**不可省** | `http.client` **既不读 `http(s)_proxy` 也不补 `User-Agent`**（urllib 两者都会做）⇒ 若 runner 侧有代理，A/D 会全灭；有这层则最坏只是「慢」，不会「死」 |
| **D** | API b64（最后兜底） | ✅ |

> 旧注释「raw 端点在 >1MB 文件上截断」的**真因是传输量太大**（cn 长连接被切），不是端点坏了 ⇒ 压缩后**同一端点即可下全**；
> 「b64 优先」实为**反向优化**（b64 无压缩 = 4× 冗余）。
> 三层叠加后的**端到端**实测：1290 文件 / 172.9 MB 冷启动 **598s**（§五②-附 2 对照表）。
> 🔴 另：**`http.client` 不带 UA ⇒ 403**（实测同一 blob：无 UA 403 / 带 UA 200）。这是本档最值得记住的一条。

## 四、半量从「静默」改「硬失败」（补 ROOT_REQUIRED 的盲区）

- ROOT_REQUIRED 只查顶层子树的**存在性** ⇒ 拦不住「顶层都在、但只同步了 1/3」这一**实际发生过**的形态。
- 新增收尾守卫：`if _budget_hit or failed:` → 打印缺失清单（前 20 项）+ `raise SystemExit("partial sync refused: synced %d/%d, failed %d, budget_hit=%s")`。
- 同时修掉 §2.2-③：失败**不再**计入 `ok`，改为独立 `failed` 列表 ⇒ 日志不再假绿，
  且 `OK source sync done:` 行现在带 `failed` / `downloaded MB` / `耗时` 三个新字段。

**为什么必须硬失败而不是告警**：半量比不同步更危险——链尾「唯一推送」会拿残缺工作区去推，
而工作区里的 `index.html` / `data/*.js` 若是上一轮的陈旧副本，会被当成「当前源码」改写后推上线（前端回退 / 陈旧数据上线）。
