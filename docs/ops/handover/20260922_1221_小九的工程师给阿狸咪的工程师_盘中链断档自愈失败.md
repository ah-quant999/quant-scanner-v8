## 三、根因（已定位到行，非猜测）

### 3.1 STOCK_QUOTE 由**独立专用链**供给，不在「盘中准点档调度器」覆盖范围

- 生产者：`algorithms/fetch_stock_quote_v8.py`
- 主链：`.github/workflows/v8_stock_quote_refresh.yml`（`runs-on: [self-hosted, cn]`，即**小九本机 cn IP**）
- 兜底：`.github/workflows/v8_stock_quote_refresh_cloud.yml`（`ubuntu-latest`，海外 IP）
- 派发源：`v8_cn_fetch_cloud.yml` 的 **relay ②**（第 1043~1105 行，阿狸咪的工程师 09-21 落地的「修法甲」门控）

这解释了为什么一级「盘中准点档调度器」dispatch 后 STOCK_QUOTE 毫无反应 —— **它本来就不负责这张卡**（与本任务记忆里 09-16/09-17 两轮实测完全一致，属**稳定复现的既有缺口**）。

### 3.2 真正的断点：主链在 11:10 后再无任何 run

主链 `v8_stock_quote_refresh.yml` 最近 run（API 实测）：

| run id | 触发 | 状态 | created (UTC) | = CST |
|---|---|---|---|---|
| 35682168620 | workflow_dispatch | success | 03:10:18 | **11:10** |
| 35680804184 | workflow_dispatch | success | 02:48:15 | 10:48 |
| 35679316100 | workflow_dispatch | success | 02:24:00 | 10:24 |
| 35677081850 | workflow_dispatch | success | 01:47:34 | 09:47 |

**最后一次 run 停在 11:10，此后 40+ 分钟零新 run。** 而 `data/STOCK_QUOTE.js` 的提交历史同样停在：

```
a96ecf887  2026-09-22T03:15:40Z   ← 最后一次写入（11:15:40 CST）
a798fe304  2026-09-22T03:14:00Z

```

### 3.3 数据面交叉验证：内容确实冻结，且非时钟问题

逐版读取两个 blob（绕过 raw 源，走 contents API）：

| blob | update_time | 提交时刻 |
|---|---|---|
| `a798fe304` | `2026-09-22 11:13:45` | 11:14 |
| `a96ecf887`（最新） | `2026-09-22 11:15:36` | 11:15:40 |

⇒ `update_time` 与「产出时刻」严格同步递增，**最后一个有效档位就是 11:15:36**（对应生成了 11:13~11:15 的行情）。**不是文件更新了但时间戳没跟上，而是内容真停。**

### 3.4 relay ② 门控为何没能救活（链式推理）

`v8_cn_fetch_cloud.yml` relay ② 的门控规则（第 1085~1101 行）：

- 主链 `queued/in_progress` 且**未超 10 分** → 不派（防叠加）
- 主链 `completed` 且 **age < 12 分** 且 `success` → 不派（判为新鲜）
- **age ≥ 12 分** → 派主链

实测矛盾点：11:10 那轮主链 run **在 11:14:09 就 completed/success**，此后 age 迅速超过 12 分，**按规则应当派发主链** —— 但实际上**一次都没派出去**。

同时注意：我在 11:57 二级 dispatch 的 `v8_cn_fetch_cloud.yml`（run 35685024954）**结论是 cancelled**，12:03 三级那轮（336661558 → 35685388269）也是 **cancelled**，只有更早的 35685408225 同样 cancelled。⇒ **这些 relay 载体 run 本身被大量 cancelled，relay ② 那段 Python 很可能根本没执行到**，门控再正确也无从生效。

（凌晨 01:47 那轮 35677066808 也是 cancelled，同一现象此前已多次出现 —— 与「队列排队被顶掉 / cancel-in-progress」家族问题同源，建议按既有 `v8-algo-chain-cancel-forensics` 手法一并查。）

### 3.5 附带发现（非本次故障主因，但属隐患）

主链日志显示：

```
new STOCK_QUOTE.js sha10 = 00b065701c
⚠️ index.html 中未找到 STOCK_QUOTE.js?v= 引用，可能已被外链替换；跳过 ?v 更新
```

⇒ `index.html` 里已无 `data/STOCK_QUOTE.js?v=` 形式的 loader 引用，缓存戳同步步**静默跳过**（脚本自身已告警，设计上允许）。建议顺带确认前端是否已改为其它注入方式；若确实已换链，则该步应清理，避免长期空跑。

## 四、下一步建议（给阿狸咪的工程师）

### 立即可做（本轮已由小九侧尝试，仍建议人工确认）

1. **手动 dispatch 主链**（最直接）：
   ```
   POST /repos/ah-quant999/quant-scanner-v8/actions/workflows/v8_stock_quote_refresh.yml/dispatches
   body: {"ref":"main"}
   ```
   主链是本机 cn IP，行情双源（新浪/东财）畅通，正常 3~4 分钟出数。
   **⚠️ 若 cn runner 离线**（run 会长期 queued），改 dispatch `v8_stock_quote_refresh_cloud.yml` 兜底。

2. **查 cn runner 是否在线**：主链 `runs-on: [self-hosted, cn]`，若 11:10 后所有 dispatch 都长期排 `queued`，即小九本机 runner 掉线（参见既有 `v8-runner-offline-false-heal` 手法）。

### 结构性（治本，建议本日内落地）

3. **relay ② 派发失败必须可见**：当前 relay ② 的 `except` 只 `print` 不报警（第 1102~1104 行「保守派主链」），且它所在的 run 一旦被 cancelled，整段逻辑静默消失。建议：
   - 给 relay ② 加**独立告警出口**（邮件/annotation），派发失败或 run 被 cancel 时可见；
   - 或将 relay ② 从「承载多次 dispatch 的云端 run」中**剥离为轻量独立 workflow**（只做门控+派发，几十秒跑完），大幅降低被 cancel 的概率。

4. **STOCK_QUOTE 陈旧须进健康巡检判据**：本次「看门狗/健康巡检全绿、但个股行情冻结 53 分钟」再次印证 **READY_SPEC 盲区** —— 巡检只查「任务有没有报错」，不查「盘中数据有没有真在动」。建议把 `data/STOCK_QUOTE.js` 的 `update_time` 新鲜度纳入 `v8_health_check.py` 的盘中判据（阈值 40 min），使这类单卡停更直接在运维页/告警里暴露，而不是只靠盘中盯守自动化发现。

5. **清理/修正 `?v` 缓存戳步**（见 §3.5）：确认 `index.html` 当前 STOCK_QUOTE 注入方式，若确已换链则删掉该死步，避免每轮 success 空跑掩盖真实问题。

6. **并入既有挂账**：本问题与「relay 载体 run 大面 cancelled」同源，建议与 `v8-algo-chain-cancel-forensics` 的整改合并处理，避免「同一 bug 二次/三次出现」。
