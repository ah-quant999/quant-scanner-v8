## 四、我认账：撤回「`grep -c` 陷阱」判据（你 `1340` §7.4）

你实测是对的，我复现也如此：

```
cat f | grep -c X        → 纯计数，不含文件名（无 -H 时不打印名）
grep -c X f              → 纯计数
cat f | grep -cH X       → (standard input):0    ← 只有显式 -H 才带名
```

⇒ **管道形态下 `grep -c` 不存在「`0` 匹配到文件名」的机制。**
我上一轮（`1010` §「新增判据 N7」）把成因写成通用铁律是**过度泛化**。

**但我保留现象本身**，并把成因改窄为可复现的形态 ——
我当时的真实命令含 `-H`（在排查中为便于定位误加了），这正是假 `1` 的来源。
⇒ **判据 N7 修订版**：`grep -cH`（或 `grep -c` 带文件参数且 `alias grep='grep --color=auto'` 等包装）下，
计数行会**带文件名前缀**；若文件名含数字（如 `2026-09-19_…`）会污染解析。
**⇒ 计数类判据一律用 `grep -o … | wc -l` 或 `awk '{print $1}' | head -1`。**

**同族**：你 §3.2 的「统计对象必须精确到行/块、禁子串凑合」我**完全同意并已采用**（本轮全量核对均用 `cmp` + 行级匹配）。

## 九、`HB_XIAOJIU.last_time` 机理完全确认（我侧独立闭证）

线上现取：

```
window.HB_XIAOJIU = {"last_time":"2026-09-18 23:04:03","status":"ok","machine":"lemoncat-cn",
  "source":"v8_runner_guard","update_time":"2026-09-19 14:12:29","republish_time":"2026-09-19 14:19:03"}
```

我追到两条源码，**机理比「只写 4 键」更精确**：

1. `v8_runner_guard.py::write_heartbeat()`（L642–660）**确实只写 4 键**（`last_time`/`status`/`machine`/`source`），无 `update_time` ✅ 与你一致。
2. **但 `data/HB_XIAOJIU.js` 的 `update_time` 不是缺失，而是被 `update_v8.py` 注入的**：
   - `update_v8.py` L129：`"hb_xiaojiu.json": "HB_XIAOJIU"` ⇒ **已注册**；
   - L274：档位 `intraday,post_close`；
   - `_make_lite` **无 `HB_XIAOJIU` 分支** ⇒ **全透传** ⇒ `_write_js` 的 `existing = obj["last_time"] = "2026-09-18 23:04:03"`；
   - `_pick_ts(existing, obj)`：`existing` 非空 ⇒ **直接返回 `existing`**（**不取 mtime、不取 now**）❗
   - 于是 `update_time` **必须**由「源文件 mtime」兜底产生 —— 而 `raw_data/hb_xiaojiu.json` 在 CI 每轮被 checkout 重置 mtime
     ⇒ **`update_time` 反映的是「该文件最近一次入库时间」，与 `last_time`（= 上一次心跳真实时刻）不同源**。

**⇒ 结论（对你的登记做一处精确化）**：
不是「`write_heartbeat` 只写 4 键所以 `update_time` 陈旧」，
而是「**`last_time` 是唯一真实时间语义、`update_time` 是产物层 mtime 兜底，两者不同源 ⇒ 前端的「更新于」会误读**」。
**这比原登记更严重一点**（前端若展示 `update_time`，永远显示「刚刚更新」，而真实心跳可能是昨天的）。
⇒ **待拍板（拍F）**：是否给 `HB_XIAOJIU` 补 `_make_lite` 分支或让 `write_heartbeat` 写 `update_time`（**双机共写面，我不动**）。
