## 3. 根因（三层，按可修性排序）

### 根因 ① 重试环假定「工作区干净」，但该 job 只提交 1 个文件

`v8_risk_gauge.yml` L41-61 的推送步，只做了：

```bash
git add raw_data/risk_gauge.json     # ← 只加这一个文件（L47）
git commit -m "v8 risk gauge: ..."   # ← L52
for i in 1 2 3; do
  if git push "$REPO" HEAD:main; then ... exit 0; fi
  echo "⚠️ push 被拒，rebase 后重试 ($i/3)"
  git fetch "$REPO" main && git rebase FETCH_HEAD || { git rebase --abort; exit 1; }   # ← L59
done
```

`git rebase` 的前置条件是**索引外无任何已跟踪文件的改动**（`require_clean_work_tree`）。该 job 从不清理工作区，**树里只要存在任何一个脏文件，rebase 就拒绝启动** —— 于是「push 被拒 → rebase 重试」这条唯一自救路径**永久失效**。

### 根因 ② 兜底 `git rebase --abort` 本身也是二次伤害

`||` 分支里写的是 `git rebase --abort; exit 1`。当 rebase **没启动过**时，`--abort` 会输出 `fatal: no rebase in progress` —— 与 ① 叠加成「双重报错」，日志里两条错误并排，极易被误读成两次故障，实际是同一处。

### 根因 ③ 本仓早有定论：CI 里不要用裸 `git rebase`（risk_gauge 是漏改的那一个）

仓库里已经写过两次结论、并已给出替代实现：

| 文件 | 行 | 现状 |
|---|---|---|
| `v8_build_deploy.yml` | L186-190 | 注释明写「**⚠️ 不要改回 git rebase**：data/*.js 是构建产物，两趟构建并发时 rebase 必然 content conflict → rebase --abort → 整个部署失败（2026-08-04 实例）」，改用 reset+全量重建 |
| `v8_cn_fetch_experiments.yml` | L109-113 | 「原写法 git fetch + git rebase + git push 必败 … **现改用 `api_push_raw.py`（Contents API，零 git fetch）**」 |
| `v8_health_patrol.yml` | L260-265 | 「原 git push + rebase 循环在并发同跑时全部失败 … **改用 Contents API（sha-based 原子更新）**」 |
| **`v8_risk_gauge.yml`** | **L54-61** | **仍是裸 `git rebase FETCH_HEAD` + `git rebase --abort` ❌ 漏改** |

⇒ **本次失败不是偶发竞争，是既定反模式的重演**。

- 零 `git fetch` / 零 rebase / 零 409；

- 与「推送走 API、不用本机 git push」的既定铁律一致。

### 乙（最小改动 · 保留 git push 时的保底）
1. L59 改为 `git -c rebase.autoStash=true rebase FETCH_HEAD`（让 rebase 自己 stash/unstash）；
2. 兜底改 `git rebase --abort 2>/dev/null || true`（未启动的 abort 不再制造二次报错）；
3. 重试前先 `git add -A && git commit --amend --no-edit`，把本 job 产生的全部改动一并纳入（避免再次「树脏」）。

## 9. 本轮新增复用要点（已记入我的巡检手册）

1. **本仓 CI 里「裸 `git rebase`」= 定时炸弹**：树一脏就拒绝启动，重试环第一步即死。见到 `error: cannot rebase: You have unstaged changes.` **别去查 push 竞争**，先查工作区为何脏。
2. **`git rebase --abort` 在 rebase 未启动时会报 `fatal: no rebase in progress`** —— 日志里这两条错误**同时出现**时，是同一处故障，不是两次。
3. **推送失败先分类**：`rejected (fetch first)` = 竞争（可重试）；`cannot rebase` = 结构性（重试无用，必须改码）。
4. **本仓已有 `api_push_raw.py` 这一既定范式**（Contents API，零 git fetch）—— 任何「加 git push 重试」的需求，默认答案就是它。
5. **`algorithms/verify_data_sanity.py` 带 CRLF blob**（全仓唯二，另一为已豁免的 `logic.html`）—— 排查「CI 工作区恒脏」时优先验证它。
