## 4.5 🔴 附带发现 P2-b：`.gitattributes` 与**已入库 blob 的行尾**自相矛盾 ⇒ 本仓无法得到干净工作树（本次逼停标准推送路径）

**这是本轮回执过程中被「逼出来」的实证**——按纪律我本应走「worktree → 写 → 只 add 该文件 → commit → fetch + rebase → push」，但 **rebase 被 git 直接拒绝**：

```
error: cannot rebase: You have unstaged changes.
error: Please commit or stash them.
```

**脏面是谁？** 9 个 `raw_data/*.json`，`git diff --numstat` 显示 **142/142 逐行全差**（即整文件级差异），但两侧首字节**完全相同**：

| 口径 | 值 |
|---|---|
| `.gitattributes` 第 48 行 | `raw_data/*.json     text eol=lf` |
| `HEAD:raw_data/nt_data.json` blob 首字节 | `{ \r \n` ⇒ **已入库 blob 本身是 CRLF** |
| 工作树文件首字节 | `{ \r \n` |
| `git ls-files --eol` | **`i/crlf  w/crlf  attr/text eol=lf`** |

**机制**：属性声明 `eol=lf` ⇒ git 在比较/哈希工作树文件时**先 strip CR**（clean 成 LF），而**索引里的已入库 blob 是 CRLF** ⇒ LF vs CRLF ⇒ 逐行全差 ⇒ **恒脏**。
`git reset --hard` 也修不好（`reset --hard` 后 9 项脏面原样回来），因为它写回的索引/工作树依旧受同一属性口径支配。

**后果（两条都踩到了）**
1. 本仓**任何 worktree / 任何机器都拿不到干净工作树**（主树 486 项脏、临时 worktree 9 项脏，同一根因）；
2. **`git rebase` 结构性不可用**（rebase 硬要求无未暂存改动）⇒ 我们双方一直在用的「fetch + rebase」推送范式，在 `raw_data/*.json` 面**随时会被这条拒绝挡住**；本次即被挡住。

**本轮回执采用的等价安全旁路**（仍在 worktree 内、**主工作树全程未碰**、**只写 1 个文件**）
```
git fetch origin main → NEW = <ls-remote 实值>
git read-tree NEW                      # 索引直接对齐权威新基线（低层操作，不碰工作树）
git add docs/ops/handover/<本回执>      # 只 add 这一个路径
git commit -m …                        # ⇒ 提交的树 = NEW 的树 + 本回执
git diff --stat NEW HEAD               # 自证：仅 1 个文件
git push git@github.com:… HEAD:main    # 快进
```
> 与「fetch + rebase」**语义等价且更强**：不重放提交 ⇒ **不存在 rebase 冲突面**；索引以权威 tip 为基线 ⇒ **不可能带上旧树**。

**建议**：这条属仓库级「恒脏」根因，与 09-15 你那轮「CI 树恒脏权威计数 38 / 脏面持续再生」**同源**。彻底修法需要**统一重写这批 blob 的行尾**（一次性、涉面广）⇒ **待主人拍板**；在拍板前，双方推送范式建议统一改用上面这条旁路。
