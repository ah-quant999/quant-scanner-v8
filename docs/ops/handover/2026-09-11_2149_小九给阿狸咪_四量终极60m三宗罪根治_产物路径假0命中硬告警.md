## 二、三宗罪（三个独立缺陷，已一次性根除）

### 罪① 产物写错目录【根因实锤】

`algorithms/strategy_four_volume_60m.py` 里有一条**硬编码的 v6 遗留分支**：只要本机存在 `E:/workspace/stock-scanner`，就把产物写进它的 `data/`，而不是当前仓库。

**CI 日志实据（`v8_algo_run.yml` run#1763 job 日志，同一批相邻两行）**：

```
▶ strategy_four_volume_60m.py  (18:40:46)  [监督执行·静默杀≥15min]
   ✅ ok |   ✅ 写出 E:/workspace/stock-scanner\data\FOUR_VOLUME_60M.js（0 只命中, 周期=60min）
▶ strategy_four_volume.py      (18:40:57)
   ✅ ok |   ✅ 写出 D:\actions\cn-runner\_work\quant-scanner-v8\quant-scanner-v8\data\FOUR_VO...
```

同批其他脚本都写 runner 工作区，**唯它写到仓库之外**。双机 active-active → **哪台装了旧仓库哪台中招**。

**修法**：删除该分支，输出目录恒为 `V8_DATA_DIR`（最高优先）或 `脚本所在仓库 ROOT/data`（与同族日线版 `strategy_four_volume.py` 完全一致的干净写法）。并新增日志回声 `[60m] DATA_DIR=…`，下次一眼可验。

### 罪② 「没扫成」被写成「今天没信号」【本地复现实锤】

活跃股池为空（数据源断连）时，脚本**仍无条件写出带新鲜时间戳的 `total:0` 产物** → 前端把它当成「今天真的没有 60m 信号」。

**本地复现输出（原始）**：

```
[东财] 连续失败3次, 进入冷却 300s
[WARN] 东方财富获取创业板列表失败(限流/重试耗尽)
    创业板: 0 只 / 科创板: 0 只 / 主板: 0 只
  股池汇总: 0 只
  ⚠️ 活跃股池为空，四量终极 60min 扫描跳过
  ✅ 写出 ...FOUR_VOLUME_60M.js（0 只命中, 周期=60min）    ← 假数据流出
```

全程仅 11 秒 → **非超时、非 baostock 登录失败，就是源断连被静默吞掉**。

**修法**：新增异常类 `ScanUnavailable`，严格区分两种情形：
- 「**扫描未能执行**」（股池空 / baostock 起不来）→ **拒绝写产物**，保留上次真实数据，**退出码 1** 上报失败；
- 「**真扫完了但命中 0 只**」→ 照常写（这是合法结果）。

> 🔴 **现场仍在复现（铁证）**：本交接起草时直查远端 —— `origin/main:data/FOUR_VOLUME_60M.js` =
> `update_time "2026-09-11 21:33:06"` / `total: 0` / `stocks: []`。
> 即 **今晚 21:33 的算法链仍在新鲜时间戳下写「0 只」假产物**（该轮早于本修复上线）。
> 这同时证明：① 产物**路径**已能落到仓库内（不再是 E:/workspace），② 但**「没扫成→写假 0」仍在**，
> ③ 前端因此把 🔔 60m 徽章显示为「今日无信号」而非报错。**下一轮 B 批（18:10 后）生效后即为验收点。**

### 罪③ 三层静默【结构性】

| 层 | 原状态 | 后果 |
|---|---|---|
| 健康检查 | `FOUR_VOLUME_60M` 在 `_LOW_FREQ_FILES` 白名单 → 24h 红线被降为「**>7 天才告警**」 | 冻结 3 天仍全绿 |
| 链尾闸门 | `verify_chain_outputs.py` 中四量 60m 仅为 **warn-only** | 不阻断、不吵 |
| 门控 | `_final_recommend_gate()` 四量 60m 走 `soft=True` 软告警 → **只打印一行** | 不入失败账本、前端不可见 |

**修法（选项 A）**：
1. 健康检查：`FOUR_VOLUME_60M` **移出白名单** + **正式登记进 `CARD_DEFS`**（「选股策略」段，`max_age=1440`，按 24h 红线判定）。
   > 白名单原理由（2026-08-27）是「baostock 60min 源本身滞后 → 常陈旧 → 会误报」；该前提**自 2026-09-03 已不成立**（脚本改为无论命中多少只都写新鲜时间戳）→ 故 **文件陈旧 ⇔ 脚本没跑成 / 产物写错地方**，属真故障，必须亮红灯。
2. 超时预算：`SCRIPT_TIMEOUT_OVERRIDE` 登记 `"strategy_four_volume_60m.py": 5400`（30→**90 分钟**）。理由：它是全链少数走 baostock 独立源 + 逐只拉 120 根 60min K 线的脚本（冷缓存慢），240 只逐只取数在源抖动时极易超 30min → 被监督器硬超时杀 → 产物写不出。
3. 门控：**软告警 → 硬告警·计败不阻断** —— 陈旧时 `FAILED_SCRIPTS.append(...)` → 写进 `raw_data/algo_run_report.json` 的 `failed_scripts` → 运维面板红灯 + 健康检查可见。
   > **仍不阻断** `final_recommend`：`final_recommend.py` 自带「60m 非今日 → 回退日线版 FOUR_VOLUME.js」降级（2026-08-31 已实证硬门控会反复阻断整轮推荐，反而让站点展示更旧的 `FINAL_RECOMMEND`）。

## 七、遗留未解（请阿狸咪夜班留意，我暂无法跨物理机验证）

🔴 **为何同晚「日线版」产出 11 只，而「60m 版」股池为 0 只？** 两脚本共用同一个 `fetch_volume_top_stocks()`（源：mootdx → 东方财富），运行时刻仅差 11 秒。两种解释：

1. 两脚本运行在**不同机器**（60m 在 cn 自托管 / 日线在云端 ubuntu）→ **网络可达性不同**（东财对海外 IP 限流更狠）；
2. 同一台机上，二者恰好落在东财**限流冷却窗口的两侧**（日志显示「连续失败 3 次进入冷却 300s」，冷却期约 5 分钟，完全覆盖这个 11 秒间隔）。

**倾向解释 1**（run#1763 日志里两脚本路径前缀不同：`E:/workspace/...` vs `D:\actions\cn-runner\...`，暗示当时 60m 走的是**另一台机器的旧工作区**）。这属于**修完罪①后需复验的下一个观察点**：若线上 60m 仍每天 0 只而日线正常，则根因是**源可达性/限流**，需给 60m 单独加源重试或换成与日线同源同机。
